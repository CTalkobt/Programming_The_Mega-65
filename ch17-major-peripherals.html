Programming the MEGA65 — Chapter 17: Major Peripherals

Oct 4, 2026 · Updated Oct 19, 2026 · @Craig Taylor

Introduction

This chapter covers the MEGA65's remaining connections to the outside world: the IEC serial bus for printers, the cartridge port, Ethernet, the serial UART, the real-time clock, and the video and audio outputs. Some correspond to C64 peripherals West described; Ethernet and the clock are new. The C64's user port and cassette port have no MEGA65 equivalent.

Printers and the IEC Bus

The IEC serial port at the rear is the same bus the C64 used, and Commodore printers and plotters connect to it exactly as before, usually as device 4 or 5. Output is sent by opening a channel to the printer and printing to it, or by redirecting all screen output with CMD:

10 OPEN 4, 4          : REM PRINTER ON DEVICE 4
20 PRINT#4, "MEGA65 PRINTER TEST"
30 CMD 4 : LIST       : REM SEND A LISTING TO THE PRINTER
40 PRINT#4 : CLOSE 4  : REM RESTORE SCREEN OUTPUT AND CLOSE

CMD can also send a string before it starts redirecting, such as a title or a printer setup code: CMD 4, "MY PROGRAM". End the redirection with PRINT# before closing, so that the last line is sent (MEGA65 Book, CMD).

Secondary addresses and control codes

On Commodore's printers the secondary address chooses the character set. OPEN 1, 4, or secondary address 0, prints upper case and graphics characters; OPEN 1, 4, 7 prints upper and lower case. Within a line, control codes printed like any other character change the style. These are the codes Commodore gave for its printers in the C64's documentation (Commodore 64 Programmer's Reference Guide, pp. 338–339):

Code Effect
CHR$(10) Line feed
CHR$(13) Return; Commodore printers add a line feed themselves
CHR$(14), CHR$(15) Start and end double-width characters
CHR$(18), CHR$(146) Start and end reverse characters
CHR$(17) Switch to the upper and lower case set
CHR$(145) Switch to the upper case and graphics set
CHR$(8) Start dot-programmable graphics 
10 OPEN 4, 4, 7                       : REM UPPER AND LOWER CASE
20 PRINT#4, CHR$(14); "REPORT"; CHR$(15) : REM DOUBLE-WIDTH TITLE
30 PRINT#4, CHR$(18); "TOTAL"; CHR$(146); 1234
40 CLOSE 4

Printers from other makers, and interfaces that connect them to the IEC bus, have their own codes and secondary addresses; consult their manuals.

Such printers often need a line feed after each return, which Commodore printers supply for themselves. BASIC 65 adds it when the channel number is 128 or more: PRINT# to such a channel ends each line with a return and a line feed instead of a return alone (MEGA65 Book, OPEN; MEGA65 ROM source, crdo). OPEN 132, 4 therefore suits a printer that needs line feeds, and would double-space on a Commodore printer.

Printing from machine language

Machine language prints through the same KERNAL routines as a disk file, which Chapter 15 used, with CHKOUT in place of CHKIN. An empty file name is enough for a printer:

        lda #0          ; data and file name in bank 0
        ldx #0
        jsr $ff6b       ; SETBNK
        lda #4          ; logical file 4
        ldx #4          ; device 4: the printer
        ldy #7          ; secondary address 7: upper and lower case
        jsr $ffba       ; SETLFS
        lda #0          ; no file name
        jsr $ffbd       ; SETNAM
        jsr $ffc0       ; OPEN
        bcs done
        ldx #4
        jsr $ffc9       ; CHKOUT: send output to file 4
        bcs done        ; for example, no printer switched on
        ldx #0
loop    lda text,x
        beq done
        jsr $ffd2       ; BSOUT: send a byte
        inx
        bne loop
done    jsr $ffcc       ; CLRCHN: output back to the screen
        lda #4
        jsr $ffc3       ; CLOSE
        rts

text    .text "HELLO FROM THE MEGA65", 13, 0

The bus and the CPU

The same bus carries disk drives and modern devices such as SD2IEC, as Chapter 15 described. The KERNAL drives it by setting and reading the bus lines itself, with the timing of the original machines. For each byte it sends or receives, and for each command such as LISTEN or UNTALK, it disables interrupts and drops the CPU to 1 MHz, then restores the speed and interrupts afterwards (MEGA65 ROM source, disk_sei, disk_cli). It slows the CPU by clearing the FAST bit in $D031, so the drop doesn't happen when full speed has been forced with POKE 0,65 or with CAPS LOCK down: the core then ignores FAST, and the transfer runs at 40.5 MHz. The core can cancel the force while the bus is active, but only when bit 1 of $D7F1 is set, and the ROM doesn't set it (mega65-core, gs4510.vhdl). A program that prints or reads a disk therefore runs slowly while it does so, and its raster interrupts can be delayed, so timing-sensitive code should not run during IEC transfers.

The Cartridge Port

The expansion port accepts C64 cartridges. Switching the MEGA65 on with a C64 cartridge in place starts it in GO64 mode, where most C64 cartridges run, though the Book warns that not all C64 software is compatible (MEGA65 Book, p. 3-13). Cartridges made for the MEGA65 can instead start in MEGA65 mode. Cartridge ROM is mapped into the 28-bit address space from $4000000 upward, where MEGA65-mode software can reach it with flat addressing or MAP, as Chapter 5 described.

How the MEGA65 starts a cartridge

At power-on the Hypervisor enables the port, resets the cartridge briefly so that cartridges which need a reset pulse are seen, and starts the machine through the C64 KERNAL's reset routine, as the C65 did. For Ultimax cartridges, which replace the KERNAL, it arranges for the cartridge's own reset vector to be used instead (mega65-core, Hypervisor main.asm, go64). The C64 reset routine looks for the C64 cartridge signature, the characters CBM80 at $8004. If it finds them it jumps through the cartridge's start vector at $8000, exactly as a C64 does, and the cartridge runs in C64 mode. Otherwise the start-up continues into MEGA65 mode (MEGA65 ROM source, C64 KERNAL start).

From ROM 920385, the MEGA65 ROM recognises cartridges made for MEGA65 mode. The change log calls the format experimental, and full auto-starting needs a newer core (MEGA65 ROM change log). During start-up the ROM reads the cartridge at $4008006 to $4008009. If bit 0 of the first byte is set and the next three bytes are "M65", it copies $2000 bytes from $4008000 to $8000 in bank 0, maps in the KERNAL and jumps to $8000; later restarts through the system vector jump to $8003 instead (MEGA65 ROM source, has_m65cart, boot_cart). The start of the cartridge's ROM is therefore laid out like this:

Offset Contents
$8000 Cold start code, normally a JMP
$8003 Warm start code, normally a JMP
$8006 Flags: bit 0 set
$8007-$8009 "M65": $4D, $36, $35

The core reaches the port's C64-style addresses at $7FF0000-$7FFFFFF, so a cartridge's I/O 1 and I/O 2 areas, $DE00-$DFFF on a C64, are at $7FFDE00-$7FFDFFF (mega65-core, slow_devices.vhdl). A few registers in the MEGA65 I/O personality control the port:

Register Purpose
$D7FB bit 1 CARTEN: 1 enables the cartridge port
$D7FD bit 6 NOGAME: must be 0 for the cartridge's /GAME line to take effect
$D7FD bit 7 NOEXROM: must be 0 for the cartridge's /EXROM line to take effect

(mega65-core, gs4510.vhdl.) The Hypervisor sets these up before starting the machine, and most programs never need to touch them.

Switch the computer off before inserting or removing a cartridge.

Ethernet

The MEGA65 has an Ethernet port. Its everyday use is file transfer with M65Connect and mega65_ftp, as Chapter 14 described, but programs can also send and receive their own network frames.

The Ethernet controller lives in the MEGA65 I/O personality. Its main registers are (MEGA65 Book, Appendix: Ethernet controller):

Register Purpose
$D6E0 Control: controller reset, transmitter reset, receive and transmit status
$D6E1 Receive and transmit buffer queue control and status
$D6E2, $D6E3 Length of the frame to transmit
$D6E4 Command register (write); reading gives the number of receive buffers
$D6E5 Receive filtering: broadcast, multicast, CRC checking, promiscuous mode
$D6E9-$D6EE The MAC address

Frames are received into, and built in, 2KB buffers at $FFDE800-$FFDEFFF. Reading there gives the receive buffer the CPU is currently looking at; writing fills the single transmit buffer, which cannot be read back. The same 2KB also appears at $D800-$DFFF, in place of colour RAM and the other I/O there, when the Ethernet I/O personality is selected with the knock $45, $54 described in Chapter 5 (mega65-core, ethernet.vhdl). The Book's Ethernet appendix says the buffers appear at $D000, but the core places them at $D800. With the knock, interrupts must be turned off first, as the Book warns, because the CIAs at $DC00 and $DD00 are out of reach until the program switches back with $47, $53. Flat addressing at $FFDE800 avoids the problem and is the better choice in machine language.

The MEGA65 has no built-in MAC address: it uses the one set on the configuration utility's Network page, and networking does not work while that is all zeros (MEGA65 Book, p. 4-7). The Hypervisor copies it into $D6E9-$D6EE at start-up (mega65-core, Hypervisor syspart.asm), and a program can read it from there while bit 1 of $D6E5 is clear:

10 FOR I = 0 TO 5
20 PRINT RIGHT$(HEX$(PEEK($D6E9 + I)), 2); : IF I < 5 THEN PRINT ":";
30 NEXT : PRINT

Receiving a frame

The controller has a ring of receive buffers, 32 of them on current boards, R3 to R6; reading $D6E4 returns the number. One buffer at a time is visible to the CPU, and the controller fills the others as frames arrive. RXQ, bit 5 of $D6E1, is set while at least one more received frame is waiting. Bits 1 and 2 of $D6E1 give the number of free buffers, but read 3 whenever three or more are free. Bit 6 of $D6E0, RXBLKD, is set when every buffer is full, and frames arriving then are lost (mega65-core, ethernet.vhdl).

To move to the next frame, write $01 and then $03 to $D6E1: the change of bit 1 from 0 to 1 frees the buffer the CPU was looking at and shows it the next one (MEGA65 Book, Ethernet appendix). These writes also clear bits 6 and 7, so they leave the Ethernet interrupts disabled. Writing 0 and then 3 to $D6E0 resets the controller and empties the ring.

Each receive buffer starts with a two-byte header (mega65-core, ethernet.vhdl):

Offset Contents
0 Frame length, low byte
1 Bits 0–2: frame length, high bits. Bit 4: multicast frame. Bit 5: broadcast frame. Bit 6: addressed to this MEGA65's MAC address. Bit 7: the frame's CRC check failed
2 onward The frame itself, starting with its destination MAC address

Frames whose CRC check fails are kept only if NOCRC, bit 1 of $D6E5, is set. This routine waits for a frame and fetches its length, using a 32-bit pointer:

ethbuf  = $fb             ; four bytes: pointer to $FFDE800

getfrm  lda #$00
        sta ethbuf
        lda #$e8
        sta ethbuf+1
        lda #$fd
        sta ethbuf+2
        lda #$0f
        sta ethbuf+3
wait    lda $d6e1
        and #%00100000    ; RXQ: is a frame waiting?
        beq wait
        lda #$01
        sta $d6e1         ; bit 1 low...
        lda #$03
        sta $d6e1         ; ...then high: show the next frame
        ldz #0
        lda [ethbuf],z    ; length, low byte
        sta len
        inz
        lda [ethbuf],z    ; flags and length, high bits
        and #%00000111
        sta len+1
        ldz #0            ; leave Z at 0, for code that uses STZ
        rts

len     .word 0

The frame's bytes then follow from offset 2. Z reaches only 256 bytes, so step ethbuf+1 for longer frames, or copy the frame out with DMA, which is much faster. A frame on a busy network can arrive every few microseconds, so a program that polls once a video frame may lose some; the Book recommends the receive interrupt, enabled with RXQEN, bit 7 of $D6E1, for serious use (MEGA65 Book, Ethernet appendix).

Sending a frame

To send, wait until TXIDLE, bit 7 of $D6E0, is set; write the frame into the transmit buffer from $FFDE800; put its length in $D6E2 and $D6E3; and write $01, STARTTX, to $D6E4. The controller adds the CRC itself (MEGA65 Book, Ethernet appendix; mega65-core, ethernet.vhdl). The frame must begin with the destination and source MAC addresses and a two-byte type, as every Ethernet frame does. This BASIC program broadcasts a minimum-size frame with type $88B5, which is reserved for local experiments:

10 B = $FFDE800
20 IF (PEEK($D6E0) AND 128) = 0 THEN 20                    : REM WAIT FOR TXIDLE
30 FOR I = 0 TO 5 : POKE B + I, $FF : NEXT                 : REM TO: EVERYONE
40 FOR I = 0 TO 5 : POKE B + 6 + I, PEEK($D6E9 + I) : NEXT : REM FROM: THIS MEGA65
50 POKE B + 12, $88 : POKE B + 13, $B5                     : REM FRAME TYPE
60 FOR I = 14 TO 59 : POKE B + I, 0 : NEXT                 : REM 46 BYTES OF DATA
70 POKE $D6E2, 60 : POKE $D6E3, 0                          : REM LENGTH
80 POKE $D6E4, 1                                           : REM SEND

Another computer on the same network can see the frame with a packet capture tool such as Wireshark. There is only one transmit buffer, so the next frame cannot be written until this one has gone.

Writing a network stack, even a simple one for UDP, is a substantial project. The Book points to WeeIP, a TCP/IP library ported to the MEGA65, at github.com/mega65/mega65-weeip, and its Ethernet appendix documents the controller in full.

The UART

The C65 included a UART, a serial port controller, and the MEGA65 keeps its registers at $D600-$D606 (MEGA65 Book, register appendix):

Register Contents
$D600 Data: the byte received or to send
$D601 Status: receive ready, framing and parity errors
$D602 Control: enable transmit and receive, character size, parity
$D603, $D604 Baud rate divisor, 16 bits: the baud rate is 7.09375 MHz divided by it
$D605, $D606 Interrupt masks and flags (not yet implemented on the MEGA65)

This is not the C64's user-port RS-232. On current boards, R3 to R6, the core does not connect this UART to any external connector, so programs cannot use it for serial communication (mega65-core, September 2026). For connecting to a PC, the usual route is the USB serial connection used by the development tools, which belongs to the serial monitor, not to this UART.

The Real-Time Clock

The real-time clock keeps the date and time while the MEGA65 is off, running from a coin-cell battery. On early R3A boards the battery is required; on R6 boards it is optional, and the clock keeps time for several days without one (MEGA65 Book, setting up). BASIC reads it through TI$ and DT$; programs can also read its registers directly at $FFD7110 (MEGA65 Book, pp. B-265, X-3):

Address Contents (binary-coded decimal)
$FFD7110 Seconds
$FFD7111 Minutes
$FFD7112 Hours
$FFD7113 Day of month
$FFD7114 Month
$FFD7115 Year
$FFD7116 Day of week, 0 to 6
$FFD7140-$FFD717F (R3);
$FFD7150-$FFD715F (R4 and later)		 Battery-backed RAM: 64 bytes on R3 boards, 16 bytes on R4 and later

The values are BCD, so $59 means 59 seconds. In BASIC:

10 RT = $FFD7110
20 S = PEEK(RT) : M = PEEK(RT + 1) : H = PEEK(RT + 2) AND $7F
30 PRINT RIGHT$(HEX$(H), 2); ":"; RIGHT$(HEX$(M), 2); ":"; RIGHT$(HEX$(S), 2)

Printing the last two digits of each value's HEX$ shows its BCD digits directly. Bit 7 of the hours register is a flag, not part of the hour, so the program masks it off, as the ROM does (mega65-core, September 2026; MEGA65 ROM source, read_rtc). The battery-backed RAM survives power-off and can store a few settings. It is small, 64 bytes on R3 boards and only 16 on R4 and later, and the Book suggests it for machine configuration, so programs should use it sparingly (mega65-core, September 2026, mega65r4_i2c.vhdl). Boards from R4 onward have extra RTC registers, documented in the Book.

TI$ gives the time as HH:MM:SS and DT$ the date as DD-MMM-YYYY, such as 19-OCT-2026. The year register holds only the last two digits, and DT$ puts "20" in front of them. Each use reads the clock afresh, and the ROM reads each register over and over until it gets the same value 256 times in a row, so that it never catches a value in the middle of changing (MEGA65 ROM source, read_rtc, Get_DT_RTC). Unlike a C64, the MEGA65 keeps TI separate: it is a timer built from CIA counters, counting seconds with a resolution of a microsecond, and has nothing to do with the clock or with TI$ (MEGA65 ROM source, Get_TI_CIA; MEGA65 Filehost, "Tips on the timer, counter, clock and RTC for the MEGA65").

The clock on R4 and later boards

On R4, R5 and R6 boards the CPU does not reach the clock chip, an RV-3032, directly. The core reads the chip's registers over its I2C bus again and again, a full pass taking a few milliseconds, and keeps a copy. Reading $FFD71xx returns that copy. Writing queues the value and the core sends it to the chip on its next pass, but it holds only one pending write at a time (mega65-core, mega65r4_i2c.vhdl, September 2026). In practice:

  • Write one byte at a time. A second write made before the first has been sent replaces it, so a loop that writes several bytes of the battery-backed RAM at full speed stores only the last one. Pause between writes; a fiftieth of a second is ample.
  • Read back after a pause too. A read straight after a write still shows the old value until the core's next pass.
  • Apart from the time and date, write only the RAM. The 64-byte block from $FFD7140 follows the chip's own register layout: the 16 bytes of RAM are at $FFD7150-$FFD715F, and $FFD714D-$FFD714F are the chip's EEPROM control registers, where a write can start an EEPROM operation. The block read from $FFD71D0 upward includes the chip's configuration, such as its power management. Writes to any of these go straight to the chip, so leave them alone; reading them is harmless (Linux RV-3032 driver).
  • Hundredths of a second are not available. $FFD7117 is meant to hold them, but current cores never copy the value from the chip, so it always reads 0. Use a CIA timer or the raster for fine timing.

Saving four bytes of settings in BASIC therefore looks like this:

10 FOR I = 0 TO 3
20 READ V : POKE $FFD7150 + I, V
30 SLEEP 0.05                     : REM LET THE CORE SEND IT
40 NEXT
50 DATA 1, 2, 3, 4

Reading the clock from machine language

The clock is outside the first megabyte, so machine language reads it through a 32-bit pointer, as the ROM does:

rtc     = $fb             ; four bytes: pointer to $FFD7110

gettime ldx #3
setp    lda rtcadr,x
        sta rtc,x
        dex
        bpl setp
        ldz #0
        lda [rtc],z       ; seconds, BCD
        sta secs
        inz
        lda [rtc],z       ; minutes
        sta mins
        inz
        lda [rtc],z       ; hours
        and #$7f          ; drop the flag in bit 7
        sta hours
        ldz #0            ; leave Z at 0, for code that uses STZ
        rts

rtcadr  .byte $10, $71, $fd, $0f
secs    .byte 0
mins    .byte 0
hours   .byte 0

A reading taken just as the seconds roll over can pair the new seconds with the old minutes. To be safe, read the seconds again at the end and start over if they have changed, or compare repeated reads as the ROM does.

Setting the clock

The usual way to set the clock is the configuration utility's Chipset page, which writes the new time to the chip as soon as RETURN is pressed; the Book's entries for TI$ and DT$ send readers there (MEGA65 Book, configuration utility, Chipset page). A program can also write the BCD values to the registers. Writes go to the chip over its I2C bus, one at a time, on both kinds of board, so pause after each one as described above (mega65-core, mega65r3_i2c.vhdl, mega65r4_i2c.vhdl).

R3 boards need one more step. Their clock chip, an ISL12020M, ignores writes to the time until bit 6 of $FFD7118 is set, and the configuration utility sets that bit before writing the time and clears it afterwards. It also sets bit 7 of the hours, so that the chip keeps 24-hour time (mega65-core, mega65_config.s, doCommitRTC). On R4 and later, $FFD7118 is one of the RV-3032's alarm registers, and no unlocking is needed. PEEK($D629) returns 3 on an R3 board and the board's revision number, such as 6, on R5 and later (mega65-core, c65uart.vhdl), so a program can tell the two apart:

10 RT = $FFD7110 : R3 = PEEK($D629) = 3
20 INPUT "HOURS (0-23)"; H$ : INPUT "MINUTES"; M$
30 IF R3 THEN POKE RT + 8, PEEK(RT + 8) OR $40 : SLEEP 0.05
40 POKE RT, 0 : SLEEP 0.05                  : REM SECONDS
50 POKE RT + 1, DEC(M$) : SLEEP 0.05        : REM MINUTES
60 POKE RT + 2, DEC(H$) OR $80 : SLEEP 0.05 : REM HOURS, 24-HOUR
70 IF R3 THEN POKE RT + 8, PEEK(RT + 8) AND $BF : SLEEP 0.05
80 PRINT TI$

DEC reads a string of hexadecimal digits, so the digits typed come out as the matching BCD value: DEC("45") is $45, which is 45 in BCD. The program does not check what is typed, and a value such as $4A would confuse the clock. The date registers are written the same way.

Video and Audio Outputs

The MEGA65 drives a VGA connector and a digital video connector at the same time. The digital output can also carry sound, which the configuration utility's Video page turns on or off; some DVI monitors need it off (MEGA65 Book, p. 4-6).

Setting Effect on programs
PAL, 720 × 576 at 50 Hz 312 VIC-II raster lines; 50 frames per second
NTSC, 720 × 480 at 60 Hz 263 VIC-II raster lines, numbered 0 to 262; 60 frames per second
CRT emulation Purely visual; no effect on programs

Bit 7 of $D06F is set in NTSC mode, so a program can adapt timing, as Chapters 8 and 13 showed. The user can switch modes in the Freezer while a program runs. A few more bits control the outputs (mega65-core, viciv.vhdl, c65uart.vhdl):

Register Effect
$D06F bit 6 VGAHDTV: use timing that suits older VGA monitors better, instead of the exact HDTV timing
$D61A bit 1 DVI: send plain DVI on the digital connector, with no sound
$D61A bit 3 Digital audio sample rate: 1 for 44.1 kHz, 0 for 48 kHz

The Hypervisor sets $D61A at start-up from the Video page's digital video setting, "enhanced (with audio)" or "dvi only (no audio)", which is bit 1 (mega65-core, Hypervisor syspart.asm, mega65_config.inc). Other bits of $D61A control other things, such as a board LED, so change one with POKE $D61A, PEEK($D61A) OR 2 or AND 253 rather than writing the whole byte.

Development cores add a 15 kHz output for CRT monitors such as the Commodore 1084S: composite sync on the VGA connector's horizontal-sync pin, with RGB on its colour pins. It is enabled by the cable, which must bridge VGA pins 12 and 15 with a 470 Ω resistor; the wiring is otherwise the same as the cable used by the C64 core. With V400 set it also interlaces this output, though not yet correctly. It is not in release 0.97 cores (mega65-core PR #934).

Audio leaves through the 3.5mm jack, which has a headphone amplifier, and through the digital video connector. The Book says the configuration utility's Audio amplifier setting turns the jack's amplifier off for line-level equipment, but on current cores it has no effect on the jack: it controls only the speaker amplifier chip on R3 boards, and development cores rename it accordingly (MEGA65 Book, configuration utility, Audio page; mega65-core PR #893; issue #735). Chapter 13 covers the mixer that feeds both.

Summary

  • Printers. OPEN a channel to device 4 or 5 on the IEC bus and use PRINT#, or redirect output with CMD. Secondary address 7 selects lower case on Commodore printers, and channels 128 and up add a line feed to each line. The KERNAL normally runs the bus at 1 MHz with interrupts off.
  • Cartridges. C64 cartridges with the CBM80 signature start the machine in C64 mode; MEGA65 cartridges carry "M65" at $8007. Cartridge ROM appears from $4000000.
  • Ethernet. Used for file transfer, and programmable through $D6E0 onward. Frames are received and sent through the buffer at $FFDE800. A MAC address must be set.
  • UART. The C65's serial controller at $D600; not connected to any external port on current boards.
  • Real-time clock. BCD time and date at $FFD7110, a little battery-backed RAM (64 bytes on R3, 16 on R4 and later), and TI$ and DT$ in BASIC. Set it in the configuration utility, or by writing the registers one at a time; R3 boards need bit 6 of $FFD7118 set first.
  • Outputs. VGA and digital video in PAL or NTSC; audio through the 3.5mm jack and digital video, which $D61A bit 1 turns off.
