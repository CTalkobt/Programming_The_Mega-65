Introduction

The VIC-IV is three video chips in one. It behaves as a VIC-II for C64 software, adds the C65's VIC-III features of 80 columns, bitplanes and a 256-colour palette, and then goes much further with its own modes. Like its ancestors it has no frame buffer: it builds each line of the display as it is drawn, from screen memory, character data and colour RAM. That design is why character graphics remain central on the MEGA65, even though it can display far more than a C64.

The native display is 720 by 576 pixels, and the chip has four banks of 256 palette entries: one for text and bitmap graphics, one for sprites, and an alternate bank that individual characters can select, so more than one palette's worth of colours can be on screen at once (mega65-core, viciv.vhdl, September 2026).

This chapter works from the easiest methods to the most detailed:

  • BASIC 65's graphics commands, which need no register knowledge
  • The registers that place screens, character sets and colour RAM in memory
  • Text modes, including the two-byte-per-character mode the MEGA65 calls SEAM
  • Full-colour and nybble-colour characters
  • The palette
  • Sprites
  • Bitplane graphics
  • Raster techniques specific to the VIC-IV
  • Software sprites built on the Raster Rewrite Buffer, and scaling their images

The VIC-II registers at $D000-$D02E work as on the C64, and the techniques in any C64 graphics reference still apply. This chapter concentrates on what is new. Most of the registers described here exist only in the VIC-IV personality, so a program starting in C64 mode must perform the knock from Chapter 5 first.

Graphics from BASIC 65

BASIC 65 has a full set of graphics commands, inherited from the C65's BASIC 10 and extended since. They draw on a bitplane screen held in banks 4 and 5, which is why Chapter 6 advised reserving those banks with MEM before using them for anything else.

Group Commands Purpose
Screens SCREEN, SCREEN CLOSE Open a graphics screen of a given size and colour depth, and close it
Drawing PEN, DOT, LINE, BOX, CIRCLE, ELLIPSE, POLYGON, PAINT Choose a colour and draw shapes and fills
Text and blocks CHAR, CUT, PASTE Draw text on a graphics screen; copy rectangular areas
Colour PALETTE, PALETTE RESTORE, BACKGROUND, BORDER, FOREGROUND Change palette entries and screen colours
Sprites SPRITE, MOVSPR, SPRCOLOR, SPRSAV Enable, move, colour and load sprites
Registers SETBIT, CLRBIT, WPOKE, WPEEK Change single bits and 16-bit values directly

A short program shows the pattern. It opens a 320 by 200 screen, draws, waits for a key, and returns to text:

10 SCREEN 320,200,4
20 PEN 1
30 LINE 0,0,319,199
40 CIRCLE 160,100,50
50 GETKEY A$
60 SCREEN CLOSE

Chapter 3 gives SCREEN's full syntax.

When to go further

The graphics commands are ideal for charts, diagrams, title screens and games where drawing speed is not critical. For fast animation, scrolling, or the VIC-IV's character-based colour modes, programs work with the registers directly. BASIC 65 makes that practical too: SETBIT, CLRBIT, WPOKE and WPEEK change bits and 16-bit registers in one statement, and many of the register examples in the rest of this chapter can be typed in as BASIC.

PALETTE RESTORE deserves a mention: it returns the system palette to its defaults, so any program that changes the palette can put things back before it ends. Every example in this chapter that changes VIC-IV state should likewise restore it, or the screen editor may be left unusable.

Where the Display Lives

The VIC-II found its screen and character set through a few bits in $D018 and the bank bits of CIA 2, which restricted them to a 16KB window. The VIC-IV replaces that with pointers that can address memory directly, at byte granularity, anywhere the chip can see.

Layout registers

Register Name Purpose
$D058-$D059 LINESTEP Bytes of screen and colour memory per character row
$D05E CHRCOUNT Characters drawn per row, low 8 bits; bits 9-8 are in $D063 bits 4-5
$D060-$D062 SCRNPTR Address of screen memory
$D064-$D065 COLPTR Offset of colour memory from $FF80000
$D068-$D06A CHARPTR Address of the character set
$D06C-$D06E SPRPTRADR Address of the sprite pointer list
$D07B DISPROWS Number of character rows drawn, minus one

LINESTEP, CHRCOUNT, SCRNPTR and COLPTR are described in Dan Sanderson's and Retrocogs' VIC-IV tutorials; check the CHARPTR and DISPROWS addresses against the MEGA65 Book (Dan Sanderson, Retrocogs).

SCRNPTR can point anywhere with byte precision, which makes coarse scrolling trivial: adding one to SCRNPTR scrolls the screen one character left. COLPTR is an offset into colour RAM rather than a full address (Retrocogs). It is 16 bits wide, but colour RAM is 32KB, so the VIC-IV uses only its low 15 bits: an offset of $8000 or more wraps round to the start of colour RAM (mega65-core, viciv.vhdl, September 2026).

LINESTEP and CHRCOUNT are separate because they answer different questions. CHRCOUNT says how many characters to draw; LINESTEP says how far apart rows are in memory. Setting LINESTEP larger than CHRCOUNT creates a screen wider than the display, which can then be scrolled horizontally by moving SCRNPTR.

Mode registers

Register Bit Name Effect when set
$D031 7 H640 80-column, 640-pixel-wide display
$D031 5 ATTR Enables VIC-III text attributes; clear it to suppress them
$D031 4 BPM Bitplane mode
$D031 3 V400 400-line vertical resolution
$D054 0 CHR16 Two bytes of screen and colour memory per character (SEAM)
$D054 1 FCLRLO Full-colour mode for screen codes 0-255
$D054 2 FCLRHI Full-colour mode for screen codes 256 and up

Hot registers

When a program writes to the C64-style registers that choose a screen or character set location, the VIC-IV calculates the equivalent address and updates its own pointers, such as CHARPTR, automatically. Five registers behave this way: $D011, $D016, $D018, $D031, and the VIC bank bits of $DD00. A write to any one of them propagates all five, so a program that has set CHARPTR directly can lose that setting simply by turning on multicolour mode in $D016 (Dan Sanderson).

Programs that manage the VIC-IV pointers themselves should turn this off by clearing HOTREG, bit 7 of $D05D:

CLRBIT $D05D,7

With HOTREG clear, the C64-style registers no longer update the VIC-IV pointers, and the program has full control. One side effect is worth knowing: the C65 shifted 80-column text slightly and compensated through the horizontal scroll bits, and the MEGA65 reproduces this. After clearing HOTREG and choosing a width with H640, set TEXTXPOS at $D04C to its standard value of 80 to place the text correctly (Dan Sanderson).

Text Modes

Text is still the VIC-IV's most important mode. The screen editor uses it, and most MEGA65 games build their graphics from characters.

Sizes

Columns × rows H640 V400 Bytes per screen (normal mode)
40 × 25 0 0 1,000
80 × 25 1 0 2,000
40 × 50 0 1 2,000
80 × 50 1 1 4,000

When changing size by hand, set LINESTEP and CHRCOUNT to match, and make sure screen memory and colour RAM are large enough. From BASIC, the editor's own screen-size commands handle this for you.

Custom screen sizes

The four sizes in the table are the only ones the screen editor knows. ESC X, ESC 4, ESC 8 and ESC 5 switch between them (Chapter 2), and WINDOW can only confine the editor to a smaller area of the current size. The VIC-IV itself has no fixed size. It draws as many rows and columns as a few registers tell it to, inside a display 800 pixels wide, so a program can have a 30-row screen, an 88-column one, or both:

Register Name Purpose Value at 80 × 25, PAL
$D048, $D049 bits 3-0 TBDRPOS Raster line where the top border ends 104
$D04A, $D04B bits 3-0 BBDRPOS Raster line where the bottom border starts 504
$D04C, $D04D bits 3-0 TEXTXPOS Pixel where the first column starts 80
$D04E, $D04F bits 3-0 TEXTYPOS Raster line where the first text row starts 104
$D05C, $D05D bits 5-0 SDBDRWD Width of each side border, in pixels 80
$D05E CHRCOUNT Characters drawn per row 80
$D058-$D059 LINESTEP Bytes from one row to the next 80
$D07B DISPROWS Number of text rows drawn, minus one 24

The vertical registers count physical raster lines. In the 25-row modes each row of character pixels is drawn on two lines, so a character row is 16 lines high, and in the 50-row modes it is 8; either way the standard text area is 400 lines tall, from line 104 to line 504 in PAL. The horizontal registers count pixels of the 800-pixel line, and the two 80-pixel side borders leave 640 for text. A write to SDBDRWD moves both side borders at once. The upper four bits of $D049, $D04B, $D04D and $D04F belong to sprite settings, and $D05D holds HOTREG in bit 7 (mega65-core, viciv.vhdl).

A bigger screen needs four things. First, HOTREG must be off: with it on, the next write to a hot register makes the VIC-IV recalculate the borders, the text position, the row count, LINESTEP and CHRCOUNT for one of the four standard sizes, undoing everything (mega65-core, viciv.vhdl). Second, the borders move apart and TEXTYPOS moves up to the new top border. Third, DISPROWS, CHRCOUNT and LINESTEP are set for the new size; for extra columns, SDBDRWD and TEXTXPOS are both set to (800 − 8 × columns) / 2. Fourth, SCRNPTR and COLPTR point at memory big enough for the screen, because the bytes after the editor's 80 × 25 screen at $0800 belong to the system (MEGA65 Filehost, "Big Screens for Fun And Profit").

This program makes an 88 × 30 screen at $50000, with its colours at offset $2000 in colour RAM, waits for a key and puts everything back. It is for PAL only: an NTSC display has 480 visible lines instead of 576, which leaves too little room above and below the standard text area.

10 REM 88 X 30 TEXT SCREEN (PAL ONLY)
20 SA=$50000 : CO=$2000 : W=88 : H=30
30 DIM R(22) : FOR I=0 TO 7 : R(I)=PEEK($D048+I) : R(I+8)=PEEK($D058+I)
40 NEXT : FOR I=0 TO 5 : R(I+16)=PEEK($D060+I) : NEXT : R(22)=PEEK($D07B)
50 EDMA 3,W*H,46,SA : REM SCREEN CODE 46 IS "."
60 EDMA 3,W*H,7,$FF80000+CO : REM YELLOW
70 FOR Y=0 TO H-1 : A=SA+Y*W
80 POKE A,48+INT(Y/10) : POKE A+1,48+MOD(Y,10) : POKE A+W-1,42 : NEXT
90 CLRBIT $D05D,7 : REM HOTREG OFF
100 WPOKE $D048,56 : WPOKE $D04A,536 : REM TOP AND BOTTOM BORDER
110 WPOKE $D04E,56 : POKE $D07B,H-1 : REM TEXTYPOS, DISPROWS
120 POKE $D05C,48 : WPOKE $D04C,48 : REM SIDE BORDER, TEXTXPOS
130 WPOKE $D058,W : POKE $D05E,W : REM LINESTEP, CHRCOUNT
140 WPOKE $D060,0 : POKE $D062,5 : WPOKE $D064,CO : REM SCRNPTR, COLPTR
150 GETKEY K$
160 FOR I=0 TO 7 : POKE $D048+I,R(I) : POKE $D058+I,R(I+8) : NEXT
170 FOR I=0 TO 5 : POKE $D060+I,R(I+16) : NEXT : POKE $D07B,R(22)

Each row starts with its number and ends with an asterisk, so the edges are easy to see. Thirty rows of 16 lines take 480 lines, from 56 to 536, and 88 columns of 8 pixels take 704 pixels, leaving 48 for each side border. Lines 30 and 40 save the registers the program changes, and lines 160 and 170 restore them; restoring $D05D also turns HOTREG back on. The WPOKEs in lines 100 to 120 clear the sprite bits in the upper half of $D049, $D04B and $D04D, which matters only to a program using those sprite features. In 80 × 50 mode, where a row is 8 lines high, the same 480 lines hold 60 rows (DISPROWS 59).

The screen editor does not know about any of this. Its row and column counts are fixed by the four standard sizes, and it finds the character it is working on from SCRNPTR but always takes colour RAM addresses from $FF80000, ignoring COLPTR (MEGA65 ROM source, setup_line). A program that stops with SCRNPTR still pointing at its own screen therefore finds READY, and anything typed after it, written into that screen at the editor's 80-column spacing. This is why the example restores the registers before it ends. Making the editor itself use extra rows means changing KERNAL variables that are not a supported interface, and may move in a later ROM.

Scaling characters

CHRXSCL, at $D05A, sets the width of text pixels in 120ths: for each pixel of the 800-pixel line, the VIC-IV moves CHRXSCL/120 pixels along the row it has built. The standard value is 120, which gives 8-pixel characters in 80-column mode. A value of 60 doubles the width of every character, so an 80-column screen shows its first 40 characters across the whole text area, each as wide as a 40-column character; 240 halves the width, so 80 characters fit in 320 pixels. Values above 240 make characters no narrower. In 40-column mode the VIC-IV halves the value first, so 120 still gives the usual 40-column characters and 240 gives 8-pixel ones (mega65-core, viciv.vhdl).

CHRXSCL scales everything drawn through the Raster Rewrite Buffer described below: text, the VIC-II-style bitmap modes, and GOTOX positions with them. Bitplanes and sprites are drawn separately and do not change. The hot registers do not reset CHRXSCL, so a program must put it back itself:

10 POKE $D05A,60 : REM DOUBLE-WIDTH TEXT PIXELS
20 GETKEY K$
30 POKE $D05A,120 : REM NORMAL WIDTH

Characters 40 to 79 of each row are now drawn beyond the right border, so lowering CHRCOUNT to 40 at the same time saves the VIC-IV work without changing what is seen. When tested, Xemu did not display CHRXSCL as the core describes, so check the result on a real MEGA65.

The vertical counterpart, CHRYSCL at $D05B, sets how many raster lines each row of character pixels is drawn on, minus one: 1 in the 25-row modes and 0 in the 50-row modes. The register description in the core calls it the number of lines per text row, but the logic counts lines per pixel row. While HOTREG is on, any write to a hot register sets it back to the standard value for the mode (mega65-core, viciv.vhdl).

Attributes

In normal text mode, each character has one byte of screen memory, its screen code, and one byte of colour RAM. The low four bits of colour RAM are the colour. The high four bits are VIC-III attributes: blink (bit 4), reverse (bit 5), bold (bit 6) and underline (bit 7), so text can be styled without a different character set. Clearing ATTR, bit 5 of $D031, switches the attributes off system-wide (Dan Sanderson).

SEAM: two bytes per character

Setting CHR16, bit 0 of $D054, switches the VIC-IV into what the MEGA65 calls Super-Extended Attribute Mode, or SEAM. Every character now takes two bytes of screen memory and two bytes of colour RAM (Retrocogs).

The extra screen byte extends the character number to 13 bits, so a screen can use up to 8,192 different characters instead of 256. The extra colour byte carries further per-character settings, and the second colour byte holds the colour itself. Among those settings, bit 7 of the first colour byte flips the character vertically and bit 6 flips it horizontally, so one character definition can be reused facing the other way (mega65-core, viciv.vhdl). Ordinary monochrome characters can then take their foreground from the first 32 palette entries, and the full-colour modes below reach the whole palette (Dan Sanderson).

Because each character now takes two bytes, LINESTEP must be at least twice CHRCOUNT: 160 for an 80-column row. The screen editor's memory is not laid out for this, so SEAM programs move SCRNPTR to their own area.

One 16-bit value is not a character. In SEAM, a screen word of $FFFF marks the end of a row: the VIC-IV stops drawing the row there, and the next row starts straight after the marker instead of LINESTEP bytes after the start of this one. Rows ended this way can therefore have different lengths, and LINESTEP does not matter for them. That makes it easy to build a screen one line at a time: write each line's characters followed by $FFFF, and the next line follows on directly. This works in release cores as well as development. A program that only wants ordinary characters must never store $FFFF in screen memory, so character $1FFF cannot be combined with all of the high screen-byte bits set (mega65-core, viciv.vhdl, September 2026).

In BASIC:

100 S1=WPEEK($D060) : S2=WPEEK($D062)  : REM SAVE SCRNPTR
110 SETBIT $D054,0                      : REM CHR16 ON
120 WPOKE $D058,160                     : REM LINESTEP 80 X 2
130 WPOKE $D060,$0000 : WPOKE $D062,$05 : REM SCREEN AT $50000
...
900 CLRBIT $D054,0 : WPOKE $D058,80     : REM RESTORE
910 WPOKE $D060,S1 : WPOKE $D062,S2

In SEAM, screen memory is written with WPOKE, low byte first. A screen code below 256 still refers to the character set at CHARPTR, so ordinary PETSCII text continues to work alongside the new modes in the next section.

Full-Colour and Nybble-Colour Characters

A C64 character has one bit per pixel: foreground or background. The VIC-IV can give a character one byte per pixel, choosing every pixel's colour directly from the palette. This is Full Colour Mode, or FCM. Nybble Colour Mode, NCM, is a lighter variant using four bits per pixel. Both require SEAM.

Full Colour Mode

In FCM each character is 8 by 8 pixels and takes 64 bytes, one per pixel. A pixel value of $00 shows the background colour, $FF shows the character's colour from colour RAM, and $01-$FE select palette entries directly (Dan Sanderson).

The most important fact about FCM, and the most common stumbling block, is that screen memory no longer holds a screen code. It holds the address of the character's 64 bytes of data divided by 64, and CHARPTR is ignored. Screen value $1000 therefore means the data at $1000 × $40 = $40000. With 13 bits available, FCM data can lie anywhere in chip RAM, aligned to a 64-byte boundary (Dan Sanderson).

Two bits in $D054 decide which screen values are treated this way:

Bit Name FCM applies to
1 FCLRLO Screen values 0-255
2 FCLRHI Screen values 256 and above

The usual choice is FCLRHI alone. Values below 256 remain ordinary characters from the character set at CHARPTR, so text and full-colour graphics share the screen, while values from 256 up point at FCM data from $4000 upward. FCLRLO would make the first 16KB of memory the only place for full-colour data, at the cost of losing the normal font, so it is rarely useful (Dan Sanderson).

A full 80 by 25 screen of unique FCM characters needs 2,000 × 64 = 128,000 bytes of data, which fits in banks 4 and 5. In return, every pixel on the screen can be any palette colour, and scrolling or animating still means changing only screen memory.

Setting up FCM in machine language

        lda #%00000001
        tsb $d054       ; CHR16: SEAM on
        lda #%00000100
        tsb $d054       ; FCLRHI: FCM for values 256 and up
        lda #<160
        sta $d058
        lda #>160
        sta $d059       ; LINESTEP = 80 characters x 2 bytes

Then point SCRNPTR at a free area, fill it with 16-bit values from $0100 upward, and place the character data at the matching addresses.

The attribute bits still apply in SEAM, in the high nybble of the second colour byte. In FCM they cut the colour that $FF pixels show to the first 16 palette entries and can make characters blink or underline; in NCM the same bits select the sub-palette, so they must not also trigger blinking or underlining (mega65-core, viciv.vhdl, September 2026). Clear ATTR, bit 5 of $D031, to suppress the attributes system-wide (Dan Sanderson). Because $D031 is a hot register, either clear HOTREG first or change $D031 before setting the VIC-IV pointers.

Nybble Colour Mode

NCM is not a separate screen mode but a property of individual SEAM characters, selected by bit 3 of the first byte of the character's colour RAM entry. Setting that bit makes the character a 4-bit full-colour character whatever FCLRLO and FCLRHI say (mega65-core, viciv.vhdl, September 2026; Dan Sanderson). Each byte of character data then holds two pixels of four bits each, and three details follow from that:

  • Pixel order is reversed. The low nybble is the left pixel and the high nybble the right one, the opposite of ordinary character data.
  • Characters are 16 pixels wide. The 64 bytes still hold 8 rows of 8 bytes, but each byte now covers two pixels, so an NCM character is 16 normal-sized pixels across. The next character on the row starts where it ends.
  • Colours come from a group of 16. The high nybble of the character's colour value supplies the upper four bits of each pixel's palette index, and the pixel's nybble supplies the lower four. A nybble of $0 is the background colour, as $00 is in FCM, and a nybble of $F shows the character's full colour value (mega65-core, viciv.vhdl, September 2026).

Because NCM characters are twice as wide, a row of them needs half as many characters to fill the screen. A full row of NCM characters is 40 characters, or 80 bytes, so LINESTEP can be 80 instead of 160. Mixing NCM and ordinary characters on one row is allowed, which is the first sign that a VIC-IV row is not a fixed grid of cells.

The Palette

The C64 had sixteen fixed colours. The MEGA65 has palettes of 256 entries, each entry an arbitrary colour chosen by its red, green and blue values. Every colour number used anywhere on the display, from border to sprite pixel, is an index into a palette.

Palette registers

Registers Contents
$D100-$D1FF Red value for entries 0-255
$D200-$D2FF Green value for entries 0-255
$D300-$D3FF Blue value for entries 0-255

Each value is 8 bits, but with its two nybbles swapped: the high nybble of the colour component is stored in the low four bits of the register, and the low nybble in the high four bits (Dan Sanderson). A red value of $A5 is therefore written as $5A. Converting at the point of storage keeps source data readable:

10 C=1 : R=255 : G=128 : B=0          : REM ENTRY 1 = ORANGE
20 POKE $D100+C, ((R AND 15)<<4) OR (R>>4)
30 POKE $D200+C, ((G AND 15)<<4) OR (G>>4)
40 POKE $D300+C, ((B AND 15)<<4) OR (B>>4)

In machine language, a 256-byte lookup table of swapped values, or a short shift-and-rotate sequence, does the same job. Tools that convert images for the MEGA65 usually swap the nybbles when they write the palette file, so the bytes can be copied straight into the registers.

The KERNAL sets the first 32 entries when it starts (MEGA65 ROM source, palette_init). Entries 0-15 follow the C64's order, so colour 2 is red and colour 6 is blue, but they are not the C64's colours. They use full-strength values, such as pure red and pure cyan, which look clean on a modern display. The C64's colours are darker and less saturated. A program that wants the C64's look can load them itself. This program, from the MEGA65 Filehost, sets the palette that the C64 mode uses (MEGA65 Filehost, "How to switch to the C64-like colors"). Its DATA values already have their nybbles swapped, so they go straight into the registers:

10 FOR C=0 TO 15 : READ V : POKE $D100+C, V : NEXT C
20 FOR C=0 TO 15 : READ V : POKE $D200+C, V : NEXT C
30 FOR C=0 TO 15 : READ V : POKE $D300+C, V : NEXT C
100 DATA 0,255,186,102,187,85,209,174,155,135,221,181,184,11,170,139
110 DATA 0,255,19,173,243,236,224,95,71,55,57,181,184,79,217,139
120 DATA 0,255,98,255,139,133,121,199,129,0,120,181,184,202,254,139

BASIC 65's PALETTE COLOR command changes an entry without any register work, and PALETTE RESTORE puts the defaults back.

Several palettes

The VIC-IV keeps four palette banks of 256 entries. $D070 chooses which bank the $D100-$D3FF registers edit (bits 7-6), which bank text and bitmap graphics use (bits 5-4), which bank sprites use (bits 3-2), and an alternate bank (bits 1-0) that a character selects with the bold and reverse attributes. Text and bitplanes share a bank; sprites can use a different one, which allows more than 256 different colours on screen at once without changing the palette mid-frame (mega65-core, viciv.vhdl, September 2026).

Development cores add BOLDISALT, bit 4 of $D053. When it is set, the bold attribute alone selects the alternate palette, without reverse, and bold no longer adds 16 to the colour. It is not in release 0.97 cores, and it is cleared at reset (mega65-core, viciv.vhdl, development).

Palette effects

Because the display reads the palette as it draws, changing an entry changes every pixel of that colour instantly. This makes some effects nearly free: fading a screen means adjusting a few dozen palette entries rather than rewriting graphics, and colour cycling, the classic technique for animating water, fire or conveyor belts, means rotating a range of entries each frame. Changing palette entries from a raster interrupt partway down the screen gives a different set of colours above and below the split.

Sprites

The VIC-IV keeps the VIC-II's eight hardware sprites and every one of their C64 registers, so $D000-$D02E sprite code works unchanged. The MEGA65 adds new options on top, all of which can be enabled per sprite.

Where the pointers are

On the C64, the eight sprite pointers sit in the last eight bytes of the screen, at $07F8 by default. In MEGA65 mode the screen is elsewhere, and at power-on the pointers are at $0FF8 (Dan Sanderson). C64 type-in programs that POKE pointers at 2040 therefore need changing, as do programs that put sprite data in memory the MEGA65 uses for other things, such as the C64's cassette buffer at $0340.

The VIC-IV can also move the pointer list anywhere: $D06C-$D06E hold its address. That is useful when screen memory is full of FCM data and the default pointer location falls in the middle of a tile (MEGA65 blog). The VIC-IV also offers 16-bit sprite pointers, so sprite data is not confined to one 16KB bank as on the C64.

New sprite features

Feature What it gives
16-colour sprites 15 colours plus a transparent one chosen per sprite; sprite n uses palette entries n×16 to n×16+15, or 128 higher with bitplane mode on (mega65-core, sprite.vhdl)
64-pixel-wide sprites Enabled per sprite in SPRX64EN, $D057: 64, 32 and 16 pixels across for hi-res, multicolour and 16-colour sprites (MEGA65 blog)

The 16-colour mode is the biggest change for game graphics. With the 64-pixel-wide option enabled, a 16-colour sprite is 16 pixels across, each pixel any of 15 colours or transparent. Combined with variable height and an eight-sprite multiplexer driven by raster interrupts, it gives arcade-quality moving objects. For more objects than that, or bigger ones, see RRB Objects.

The MEGA65 Book lists the enable registers for 16-colour mode, height and high-resolution positioning.

Sprites from BASIC

BASIC 65's SPRITE command turns sprites on and sets their colour, size and mode; MOVSPR moves them, optionally along a path at a set speed; SPRCOLOR sets the shared multicolour registers; and SPRSAV copies sprite data to and from strings. SPRITE switches a sprite between monochrome and VIC-II multicolour, and from ROM 920415 SPRITE SYS R turns on high-resolution sprites (MEGA65 ROM change log). BASIC does not support 16-colour and the other VIC-IV sprite modes (Dan Sanderson), so for those, BASIC programs set the registers directly with SETBIT and POKE.

Bitplanes

The C65 introduced bitplane graphics, the Amiga's way of building a colour image: several one-bit-per-pixel images, the bitplanes, are overlaid, and the bits at each pixel position combine into a palette index. With n bitplanes there are 2ⁿ colours, up to 8 bitplanes and 256 colours.

Setting Options
Mode BPM, bit 4 of $D031, selects bitplane graphics
Width 320 or 640 pixels, by H640
Height 200 or 400 lines, by V400
Depth 1 to 8 bitplanes

On the C65, $D032 chooses which bitplanes are displayed and $D033-$D03A hold their addresses. These are VIC-III registers, so they are reached in the VIC-III or VIC-IV personality.

Memory

Each bitplane of a 320 by 200 screen takes 8,000 bytes, and memory grows with each step up in size or depth:

Screen Bytes per bitplane 4 bitplanes (16 colours) 8 bitplanes (256 colours)
320 × 200 8,000 32,000 64,000
640 × 200 16,000 64,000 128,000
640 × 400 32,000 128,000 256,000

The larger combinations exceed the 128KB of banks 4 and 5, so high resolutions are normally used with fewer colours. BASIC 65's graphics commands draw on bitplane screens in banks 4 and 5, which is why SCREEN takes a depth argument.

Bitplanes or full-colour characters?

For a static picture, either works. For anything that moves, full-colour characters are usually better. Moving an object across a bitplane screen means rewriting bits in several planes; moving it across a character screen means changing a few screen codes. FCM also lets repeated tiles share one copy of their data, while bitplanes store every pixel individually. Bitplanes suit drawing programs, line graphics and images with no repetition; characters suit games, scrolling and user interfaces.

Raster Techniques

Chapter 8 showed raster interrupts with the VIC-II registers. On the MEGA65 they power the same effects as on the C64, such as split screens, colour bars and sprite multiplexing, and at 40.5 MHz there is far more time to do work between interrupts. The VIC-IV also offers something the C64 never had: a way to draw characters on top of other characters, at any horizontal position, without using sprites.

The Raster Rewrite Buffer

The VIC-IV builds each line of the display in an internal buffer before sending it to the screen. The bytes of a row in screen and colour memory act as a list of drawing instructions: fetch this character, paint its pixels, move right by its width. Usually each instruction draws a character. A special instruction instead moves the drawing position, and because it can move backwards, later characters can be drawn over earlier ones. That buffer is called the Raster Rewrite Buffer, or RRB, and it is the basis of layered, parallax and many-object graphics on the MEGA65 (Dan Sanderson).

GOTOX

The position-moving instruction is called GOTOX. It occupies one character slot in SEAM, two bytes of screen memory and two of colour memory, and is marked by bit 4 of its first colour byte:

Byte Bits Meaning in a GOTOX entry
Colour byte 0 4 GOTOX flag: this entry is an instruction, not a character
Colour byte 0 7 Transparency: colour 0 in following characters does not overwrite the buffer
Screen byte 0 7-0 New X position, bits 7-0, in pixels from the left border
Screen byte 1 1-0 New X position, bits 9-8
Screen byte 1 7-5 Y offset of 0 to 7 pixels for the following characters, drawing each one that many rows higher
Screen byte 1 4 Subtract the Y offset instead, drawing the following characters lower (core 0.97 and later)
Colour byte 0 3 ROWMASK: draw the following characters only on the pixel rows whose bits are set in colour byte 1
Colour byte 1 7-0 The row mask, one bit per pixel row, used when ROWMASK is set
Colour byte 0 6 Treat the following characters as background, for sprite priority
Colour byte 0 2 Treat the following characters as foreground, for sprite priority

To draw a soldier on a patch of flowers, a row contains three entries: the flower character, a GOTOX back to the flower's X position with transparency set, and the soldier character. The soldier's colour-0 pixels let the flowers show through. Transparency stays on for the rest of the row, or until another GOTOX changes it (Dan Sanderson).

The Y offset and the row mask together let an object move vertically by single pixels within a character row: offset its character, and mask off the rows that would otherwise spill into the row above or below. The offset, row mask and priority settings, like transparency, last for the rest of the row or until the next GOTOX (mega65-core, viciv.vhdl, release 0.97). On release 0.97 cores, a GOTOX with ROWMASK set whose row mask has bits 5 and 6 both set also switches the following characters to the alternate palette, as bold and reverse do; development cores fix this (mega65-core PR #928).

Organising layers

Three ways of arranging a row are common:

  1. Stacks per position. At each place on the row, draw every layer's character with a GOTOX between them. Compact, but changing one object means rebuilding the row.
  2. Full layers. Draw a whole row of background, GOTOX to 0 with transparency, a whole row of the next layer, and so on. Simple to address, since every layer has a fixed offset, but sparse foreground layers waste memory on empty characters.
  3. Background plus draw list. Draw the full background, then a list of GOTOX and character pairs for the objects on that row. Economical, at the cost of rebuilding each row's list when objects move.

Whichever is used, the row must end with a GOTOX to the right border followed by a character, or the VIC-IV treats the last drawing position as the end of the line and leaves the rest of it blank (Dan Sanderson).

Sizing rows

GOTOX entries use character slots, so CHRCOUNT must cover every character and every GOTOX in the busiest row, and LINESTEP must be at least twice CHRCOUNT in SEAM. Making LINESTEP a power of two, such as 128 rather than the minimum 124, wastes a few bytes but makes row addresses quick to compute in machine language.

Time limits

The VIC-IV has only so long to fill the buffer for each line. Its "double buffering", which prepares one line while drawing the previous one, should be left on by keeping NORRDEL, bit 7 of $D051, clear. At 200 lines, the time available can be doubled by setting V400, setting CHRYSCL at $D05B to 0, setting DBLRR, bit 6 of $D051, and moving TEXTYPOS at $D04E up by two pixels. In one test, twelve rows of 20 NCM characters handled 11 full layers before lines started to go missing (Dan Sanderson).

The limits differ slightly between real hardware and the Xemu emulator, so test RRB-heavy code on both. Bit 5 of $D60F, REALHW, reads 1 on a real MEGA65 and 0 in Xemu, if a program needs to adjust.

The cycle budget

The VIC-IV builds each line while the line before it is on the screen, clocked at 81 MHz, three times the 27 MHz rate at which pixels go to the display. A PAL line is 864 pixels long and an NTSC line 858, so there are about 2,590 cycles per line in PAL and 2,570 in NTSC to fetch and draw everything on the next line. When the characters are done, the sprite data for the line is fetched in the same time, so sprites take a share too. With DBLRR set, a line is built only every second raster line, which doubles the time (mega65-core, viciv.vhdl, frame_generator.vhdl, pixel_driver.vhdl).

Drawing a character into the buffer takes one cycle per pixel, whether the pixel is transparent or not: 8 cycles for an ordinary or FCM character and 16 for a 16-pixel-wide NCM character. The VIC-IV draws one character while it fetches the next, so the total per character is not simply fetch plus draw (mega65-core, viciv.vhdl). Working estimates, worked out by MEGA65 game developers, reviewed by the core's designer and checked against a game close to the limit, are:

Entry Cycles (estimate) Per line, about
Monochrome character 11 230
Multicolour character, single-width pixels 12 210
FCM character 18 140
NCM character 26 98
GOTOX 2 —

The last column assumes about 2,550 cycles for the whole line (MEGA65 Filehost, "RRB Time Calculations"). The figures are for planning, not guarantees: add up the busiest row, leave a margin for sprites, and test. By this reckoning a 40-column row of FCM characters with a second full FCM layer and two GOTOX entries needs about 1,450 cycles and fits easily, while five full layers of 20 NCM characters need about 2,600 and do not fit without DBLRR.

Running out of time

By default the VIC-IV never abandons a line it has not finished. It carries on into the time meant for the next line, which then is not built properly, so lines go missing or are garbled, as in the test above. Setting NORRBWRAP, bit 3 of $D07C, makes the VIC-IV stop a late line when the next one is due to start, so only the unfinished part of that line is lost (mega65-core, viciv.vhdl).

The same bit controls wrap-around. The drawing position is 10 bits wide, so normally drawing past position 1023 continues at 0, the first pixel of the text area. A GOTOX to 1024 − n therefore puts a character n pixels to the left of the first column, with only its right-hand part visible, which lets objects slide in from the left edge. With NORRBWRAP set, drawing stops at the end of the buffer instead (mega65-core, viciv.vhdl).

An RRB demo in BASIC

This program draws a checked pattern on a 40-column SEAM screen and moves three balls across it, each on its own row, using no sprites. Every row has 44 entries: 40 pattern characters, a GOTOX with transparency, the ball (or a space), a GOTOX to 320, the right edge in 40-column mode, and one more character after it. So CHRCOUNT is 44 and LINESTEP 88.

10 REM RRB DEMO: BALLS OVER A PATTERN
20 SA=$50000 : CA=$FF82000 : W=88
30 DIM R(13) : FOR I=0 TO 13 : R(I)=PEEK($D058+I) : NEXT
40 TX=WPEEK($D04C) : HR=PEEK($D05D)
50 FOR Y=0 TO 24 : A=Y*W
60 FOR E=0 TO 39 : WPOKE SA+A+E*2,102 : WPOKE CA+A+E*2,$0B00 : NEXT
70 WPOKE SA+A+80,0 : WPOKE CA+A+80,$0090 : REM GOTOX 0, TRANSPARENT
80 WPOKE SA+A+82,32 : WPOKE CA+A+82,$0100 : REM OBJECT (A SPACE)
90 WPOKE SA+A+84,320 : WPOKE CA+A+84,$0010 : REM GOTOX 320
100 WPOKE SA+A+86,32 : WPOKE CA+A+86,$0100 : NEXT
110 FOR Y=6 TO 18 STEP 6 : WPOKE SA+Y*W+82,81 : NEXT : REM BALLS
120 CLRBIT $D05D,7 : CLRBIT $D031,7 : WPOKE $D04C,80
130 SETBIT $D054,0 : WPOKE $D058,W : POKE $D05E,44
140 WPOKE $D060,0 : POKE $D062,5 : WPOKE $D064,$2000
150 FOR X=0 TO 312
160 WPOKE SA+6*W+80,X : WPOKE SA+12*W+80,312-X
170 WPOKE SA+18*W+80,MOD(X*3,313) : SLEEP 0.02 : NEXT
180 SETBIT $D031,7 : CLRBIT $D054,0
190 FOR I=0 TO 13 : POKE $D058+I,R(I) : NEXT
200 WPOKE $D04C,TX : POKE $D05D,HR

Lines 50 to 100 build the rows. Screen and colour words are written low byte first, so $0090 puts $90 in the first colour byte: the GOTOX flag ($10) and transparency ($80). $0B00 leaves the first colour byte clear and puts colour 11, dark grey, in the second, and $0100 makes the ball white. Screen code 102 is the checked character and 81 the ball. Lines 120 to 140 clear HOTREG, switch to 40 columns, turn on SEAM and point SCRNPTR and COLPTR at the new screen and its colours, which are at offset $2000 in colour RAM.

Moving a ball needs one WPOKE: the X position in its row's first GOTOX, in 40-column pixels from 0 to 319. Because transparency is on, the pattern shows through the corners of the ball. Nothing is copied or erased as the balls move, which is what makes the RRB cheap for many objects. Lines 180 to 200 put the screen back, including HOTREG, so the program ends at an ordinary READY prompt.

Smooth scrolling

The VIC-IV also scrolls more freely than the VIC-II. Coarse scrolling is a matter of changing SCRNPTR and COLPTR, which can point anywhere, so a map wider than the screen needs only a larger LINESTEP and a moving pointer. Fine scrolling uses the pixel-level text position registers, TEXTXPOS at $D04C and TEXTYPOS at $D04E, together with one extra character per row so the partly visible column at the edge is filled (Retrocogs). Parallax layers combine scrolling with the RRB: each layer is a section of the row whose GOTOX position is offset by a different amount.

RRB Objects

The ball demo above is a software sprite in miniature: a shape drawn into the Raster Rewrite Buffer at any X position, over a background that is never disturbed. This section turns that idea into a small object library, first in BASIC and then in machine language, which moves multi-character full-colour objects freely in both directions. It ends with ways to scale an object's image.

The programs in this section are on the chapter's disk image, ch12.d81, as RRB OBJECTS, RRB OBJECTS ML, RRB ZOOM and RRB SCALE, alongside the machine-language routine RRBOBJ, so the BLOAD in RRB OBJECTS ML finds it. The downloads for the listings that only add or change lines are the complete, merged programs. The BASIC text files suit reading and Xemu's -importbas option; the PRG files and the disk image run on a MEGA65 as they are.

Planning the library

The library uses the "background plus draw list" arrangement from Organising layers, simplified so that each object owns a fixed slot in every row. A row of the 40-column SEAM screen has 54 entries:

Entries Byte offset Contents
0-39 0-79 Background characters
40-42 80-85 Object 0: a GOTOX with transparency, then its left and right glyphs
43-51 86-103 Objects 1 to 3, the same way
52-53 104-107 GOTOX 320 and one character, to end the row

CHRCOUNT is therefore 54. The 108 bytes of a row are spaced 128 apart, so LINESTEP is 128, which makes a row address a simple shift in machine language. On rows an object does not touch, its two glyphs are a blank, so the slot draws nothing. Later slots are drawn over earlier ones, so the slot order is the priority order.

Every slot costs time on every row, used or not. By the estimates in The cycle budget, a slot of one GOTOX and two FCM characters is about 38 cycles, and the 40 monochrome background characters about 440. Four objects bring a row to about 600 cycles of the 2,550 available, so slots for about fifty objects of this size would fit before sprites need their share. Beyond a handful of objects, games build a short list for each row instead, holding only the objects that touch it.

Storing the images

An object is 16 by 16 pixels: two strips, each one FCM character wide and two characters tall. The glyphs of a strip are stored one after the other, with a blank glyph before and after, so one image takes seven glyphs:

glyph   +0     +1      +2      +3     +4      +5      +6
        blank  left    left    blank  right   right   blank
               top     bottom         top     bottom

Because FCM glyphs are 64 bytes and each pixel row is 8 bytes, consecutive glyphs form one continuous strip 8 pixels wide: pixel (x, y) of a strip is at its first glyph's address + 8y + x, across the boundary between glyphs. The blanks are what the vertical positioning below reads when it runs off either end of a strip. The library keeps two blank glyphs at $40000 and $40040 (glyph numbers $1000 and $1001), uses $1001 to switch a slot off, and puts the first image at glyph $1002, address $40080. FCLRHI is on, so the background's screen codes below 256 still come from the normal character set.

Vertical positioning

The Y offset in a GOTOX entry, screen byte 1 bits 7-5, moves the following characters up to 7 pixels; setting bit 4 as well moves them down instead (GOTOX). It works by changing which bytes of glyph data the VIC-IV fetches: it adds the offset to, or subtracts it from, the glyph's pixel-row address, so the rows it needs from beyond the glyph come from the glyph before or after it in memory. That is why the offset applies only to FCM and NCM characters, whose data is found by glyph number, and why the strips have blanks at each end (mega65-core, viciv.vhdl, October 2026).

To put an object at pixel row Y, take character row R = INT(Y/8) and D = Y − 8R. The object covers rows R, R+1 and R+2. In row R+J its slot holds a GOTOX to the object's X position with a downward offset of D, then glyph J of each strip:

  • Row R shows the blank on its first D pixel rows and the top 8 − D rows of the top glyphs below that.
  • Row R+1 shows the bottom D rows of the top glyphs, then the top of the bottom glyphs.
  • Row R+2 shows the bottom of the bottom glyphs, then the blank.

When D is 0 the third row is all blank, but writing it anyway keeps the code simple. The downward offset needs core 0.97 or later. On earlier cores, when D is not 0, the same result comes from the upward offset, 8 − D, with each row using the glyph before.

The screen word of the GOTOX is then X + $1000 + D × $2000: X in bits 9-0, the downward flag in bit 12 and the offset in bits 15-13. Its colour word stays $0090, GOTOX plus transparency.

Objects from BASIC

This program builds the screen, draws a ball into the image, and bounces four copies of it around over a checked background. The subroutine at line 1000 is the library: it blanks an object's slot in the rows it used last time and writes it into the rows it covers now.

Lines 70 to 90 draw the ball pixel by pixel into the two strips, in red (2) with a white (1) highlight; pixel value 0 is transparent. Lines 100 to 160 build each row as in the table above. The glyph entries have a colour word of 0, since FCM pixels choose their own colours. Lines 170 to 190 set up the screen as in the earlier demo, with FCLRHI added and 54 entries per row. Lines 280 to 300 put everything back.

The subroutine needs only X(N), Y(N) and IG(N), the image's first glyph. The array OW remembers the row each object was drawn at last, with 99 meaning never. Because each object has its own image number, animation is a matter of pointing IG(N) at another seven-glyph image before the next call.

Clipping at the edges

The subroutine accepts X from −15 to 319 and Y from −15 to 199, and the hardware clips the rest. On the right, anything past pixel 319 is drawn under the border. On the left, a negative X becomes a GOTOX to 1024 + X, which wraps round to the left edge (Running out of time); NORRBWRAP must be clear. At the top and bottom, rows outside 0-24 are simply not written, and the offset arithmetic still puts the visible part in the right place, because INT rounds a negative Y down.

A character can also be made narrower. In an ordinary SEAM character entry, not a GOTOX, screen byte 1 bits 7-5 trim 0 to 7 pixels from its right-hand side, and for 16-pixel NCM characters bit 2 of colour byte 0 supplies a fourth bit, for up to 15. An object whose width is not a multiple of 8 can end with a trimmed glyph, and the characters after it start where it ends (mega65-core, viciv.vhdl, October 2026).

The update in machine language

The BASIC subroutine is clear but slow, and an object can be drawn half-moved if the raster passes while it runs. This routine does the same work for all four objects in a tiny fraction of a frame, using the same screen. It lives in the area BASIC leaves free at $1600 (Chapter 9), with a table of object positions at the start, and uses the top of a private base page at $1700 for its pointers.

; RRB object update: four 16x16 FCM objects on the screen
; at $50000 built by the BASIC program, 128 bytes per row
        * = $1600
objx    .word 0, 0, 0, 0        ; $1600: X, 0-319 or 1009-1023
objimg  .word 0, 0, 0, 0        ; $1608: first glyph of each image
objy    .byte 0, 0, 0, 0        ; $1610: Y, 0-199
oldrow  .byte $ff, $ff, $ff, $ff ; $1614: row last drawn, $FF = none
slot    .byte 80, 86, 92, 98    ; $1618: slot offset within a row

ptr     = $f0           ; four-byte flat pointer, base page $17
crow    = $f4
count   = $f5
gxlo    = $f6           ; GOTOX screen word
gxhi    = $f7
glo     = $f8           ; glyph of the left strip
ghi     = $f9
blank   = $1001         ; empty glyph, with another before it

        * = $1620
update  lda #$17
        tab             ; private base page at $1700
        ldx #3
uloop   jsr clear       ; take object X off its old rows
        jsr draw        ; and put it on its new ones
        dex
        bpl uloop
        lda #$00
        tab             ; base page 0 again for BASIC
        ldz #$00
        rts

rowptr  sta crow        ; A = character row, X = object
        lsr a
        sta ptr+1       ; row * 128, high byte
        lda #$00
        ror a           ; row * 128, low byte: $00 or $80
        ora slot,x      ; slot offsets are below 128: no carry
        sta ptr
        lda #$05
        sta ptr+2       ; bank 5
        lda #$00
        sta ptr+3
        lda #3
        sta count       ; an object covers three rows
        rts

nextrow lda ptr         ; add 128 to the pointer
        eor #$80
        sta ptr
        bmi samepg      ; bit 7 now set: no carry
        inc ptr+1
samepg  inc crow
        rts

clear   lda oldrow,x
        cmp #$ff
        beq cdone       ; never drawn
        jsr rowptr
cloop   lda crow
        cmp #25
        bcs cdone       ; below the last row
        lda #<blank
        ldz #2
        sta [ptr],z     ; left glyph, low byte
        ldz #4
        sta [ptr],z     ; right glyph, low byte
        lda #>blank
        ldz #3
        sta [ptr],z
        ldz #5
        sta [ptr],z
        jsr nextrow
        dec count
        bne cloop
cdone   rts

draw    lda objy,x
        lsr a
        lsr a
        lsr a           ; character row = Y / 8
        sta oldrow,x
        jsr rowptr
        lda objy,x
        asl a
        asl a
        asl a
        asl a
        asl a           ; Y AND 7 into bits 7-5
        ora #$10        ; bit 4: move the characters down
        sta gxhi
        txa
        asl a
        tay             ; Y register = 2 * object, for word tables
        lda objx+1,y
        and #$03
        ora gxhi        ; X bits 9-8 into bits 1-0
        sta gxhi
        lda objx,y
        sta gxlo
        lda objimg,y
        sta glo
        lda objimg+1,y
        sta ghi
        inw glo         ; skip the blank: left strip, top glyph
dloop   lda crow
        cmp #25
        bcs ddone
        ldz #0
        lda gxlo
        sta [ptr],z     ; GOTOX
        inz
        lda gxhi
        sta [ptr],z
        inz
        lda glo
        sta [ptr],z     ; left strip glyph
        inz
        lda ghi
        sta [ptr],z
        inz
        clc
        lda glo
        adc #3
        sta [ptr],z     ; right strip glyph, three glyphs on
        inz
        lda ghi
        adc #0
        sta [ptr],z
        inw glo         ; next glyph down the strip
        jsr nextrow
        dec count
        bne dloop
ddone   rts

ROWPTR works out the flat address of an object's slot. With 128 bytes per row, the row number shifted right once is the high byte and the bit shifted out becomes bit 7 of the low byte, so no multiplication is needed. NEXTROW adds 128 the same way. DRAW builds the GOTOX word from the low three bits of Y and the ten bits of X, then writes the GOTOX and both glyph numbers for each of the three rows. Only screen memory changes; the colour words set up by BASIC never do. INW is used for the glyph number because it carries into the high byte.

Calling it from BASIC

The machine-language version takes Y from 0 to 199 only; above that it would need the negative-row handling of the BASIC subroutine. A game written entirely in machine language would call UPDATE from a raster interrupt below the last text row, so the screen never shows an object half-moved.

Texture scaling

The VIC-IV has no scale setting for individual characters. In SEAM, the screen and colour bytes of a character select its glyph, flips, width trim, NCM and attributes, but nothing that changes its size (mega65-core, viciv.vhdl, October 2026). There are two ways round this: scale the whole display, or scale the image data.

Scaling the whole display

CHRXSCL and CHRYSCL, described in Scaling characters, stretch everything the RRB draws. GOTOX positions are pixels of the buffer, so they scale with it, and objects stay in place over the background as the scene zooms. Adding one line to the object program makes the whole scene grow to double width, from the left edge, every 60 frames:

265 POKE $D05A,120-MOD(T,60)

Line 290 already restores CHRXSCL, because it is one of the registers saved from $D058. The VIC-IV applies CHRXSCL as it sends each line to the screen, so a raster interrupt can change it partway down to give different bands different widths, as in a perspective road or floor (mega65-core, viciv.vhdl). Check the result on a real MEGA65, for the reason given in Scaling characters.

Scaling an object with DMA

To change the size of one object, redraw its glyphs at the new size. DMAgic does this with fractional steps (Chapter 8). Options $82 and $83 set the source step in 256ths of a byte and whole bytes, and DMAgic keeps the fraction as it goes, so a step of 2.0 reads every second byte and 0.5 reads each byte twice. Options $84 and $85 do the same for the destination. Every option goes back to its default when the last job of a list finishes (mega65-core, gs4510.vhdl, October 2026).

The strip layout makes this simple. A pixel column of a strip is a run of bytes 8 apart, so one DMA job with a destination step of 8 writes a whole column. If the source texture is stored column by column, each column a run of consecutive bytes, the source step is texture height ÷ new height: one job scales one column vertically. Choosing which texture column feeds each new column scales it horizontally. This is how a raycasting game draws its walls. It works for FCM, where each byte is a pixel; NCM packs two pixels into a byte and would need a different layout.

These lines add a 32 × 32 texture to the object program and redraw object 0 every frame at a size from 1 to 16 pixels, centred in its 16 × 16 image. Object 0 gets an image of its own at glyph $1009, straight after the ball's seven glyphs, so the other three balls are unchanged:

212 IG(0)=IM+7 : GB=IG(0)*64 : S=16 : SS=-1 : GOSUB 400 : GOSUB 500
266 S=S+SS : IF S<2 OR S>15 THEN SS=-SS
267 GOSUB 500
400 REM TEXTURE AND DMA LIST, ONCE
410 FOR PX=0 TO 31 : FOR PY=0 TO 31 : C=0
420 IF (PX-15.5)^2+(PY-15.5)^2<240 THEN C=5+8*MOD(INT(PX/4)+INT(PY/4),2)
430 POKE $42000+PX*32+PY,C : NEXT : NEXT
440 FOR I=0 TO 18 : READ B : POKE $5F000+I,B : NEXT
450 DATA 10,130,0,131,0,133,8,0,0,0,0,0,32,4,0,0,4,0,0
460 RETURN

520 POKE $5F002,MOD(V,256) : POKE $5F004,INT(V/256) : WPOKE $5F009,S
530 FOR PX=0 TO S-1 : Q=PX+O
540 WPOKE $5F00B,$2000+INT(PX*32/S)*32
550 WPOKE $5F00E,GB-$40000+(1+INT(Q/8)*3)*64+O*8+MOD(Q,8)
560 POKE $D702,5 : POKE $D704,0 : POKE $D701,$F0 : POKE $D705,0 : NEXT
570 RETURN

Lines 410 to 430 draw a green chequered disc into the texture at $42000, one 32-byte column at a time. Lines 440 and 450 place a DMA list in bank 5, at $5F000:

Offset Bytes Meaning
0 $0A F018A list format
1-4 $82 lo $83 hi Source step, set by line 520
5-6 $85 $08 Destination step: 8 bytes, one pixel row
7 $00 End of options
8 $00 Command: copy
9-10 count New height, set by line 520
11-13 source Texture column, bank 4, set by line 540
14-16 destination Image column, bank 4, set by line 550

Line 510 clears the image and works out the margin O and the source step V, which is 32 ÷ S in 256ths: 8192 ÷ S. Rounding V down keeps the last row read inside the column. Each pass of the loop picks a texture column, points the job at it and at one column of the image, and starts the job. Line 560 writes the list's bank before its megabyte and the low byte last, which starts it, as in Chapter 8.

Shrinking needs no extra code, but enlarging does: an image bigger than the texture shows each texture pixel two or more times, and the object must have strips enough to hold it. Because the image is rewritten while it is on screen, object 0 may flicker. A program that minds keeps two images for the object, scales into the one not being shown, and then switches IG(0).

Scaling from machine language

In machine language the list is the same, written with labels. This is one column scaled from 32 to 16 pixels, with a source step of exactly 2:

column  .byte $0a       ; F018A format
        .byte $82, $00  ; source step: 0/256 ...
        .byte $83, $02  ; ... plus 2 whole bytes
        .byte $85, $08  ; destination step: one pixel row
        .byte $00       ; end of options
        .byte $00       ; command: copy
        .word 16        ; new height
        .word $2000     ; texture column 0 at $42000
        .byte $04
        .word $00c0     ; left strip: image at $40080, + 64
        .byte $04
        .word $0000     ; modulo, unused

        lda #$00
        sta $d702       ; list in bank 0
        sta $d704       ; megabyte 0, written after $D702
        lda #>column
        sta $d701
        lda #<column
        sta $d705       ; start the enhanced job

A routine that scales a whole object patches the count, source and destination for each column, or builds one chained job per column and starts them all with one trigger. In a chain, each job still begins with its own option list, even if that is only the $00 that ends it, and the steps set by the first job carry over until the chain ends.

Going further

  • More objects. Replace the fixed slots with a list per row, rebuilt each frame from the objects that touch that row, so rows without objects cost nothing extra.
  • Bigger objects. Add strips, and a row for each extra glyph of height. The arithmetic is unchanged: strip s, glyph j of an image whose strips are h glyphs tall is glyph 1 + s(h + 1) + j.
  • NCM objects. NCM glyphs are 16 pixels wide and use half the memory per pixel of FCM, and the Y offset works on them too. They cost more cycles per glyph (The cycle budget).
  • Frame timing. Run the update from a raster interrupt, as in Chapter 8, so that objects move once per frame and never tear.

Plotting Pixels and Drawing Lines

On bitplane screens opened by BASIC 65, DOT plots a pixel and LINE draws a line, and nothing more is needed. This section gives machine-language equivalents for every mode in this chapter: one plot routine per mode, and a single line routine that works with all of them by calling the plot routine through a vector.

The routines favour clarity over speed. Each plot computes its address from scratch, using the hardware multiplier from Chapter 5 for the row and the Q register from Chapter 7 for the 32-bit sum, then writes through a flat [ptr],Z pointer so the bitmap can be anywhere in memory. A faster version would precompute a table of row addresses.

Address formulas

All of these modes store the screen in 8-line cell rows, so each formula has the same shape: a cell-row offset, plus an offset within the row. Here cw is the cell width in pixels and rowbytes the bytes per cell row.

Mode Bits per pixel Cell width (cw) rowbytes at 320 wide
VIC-II hi-res bitmap, bitplane, monochrome SEAM quilt 1 8 320
VIC-II multicolour bitmap 2 4 320
FCM quilt 8 8 2,560
NCM quilt 4 16 1,280

The byte offset of pixel (x, y) in each mode:

1 bit:    (y/8)*rowbytes + (x AND $FFF8) + (y AND 7)
          bit mask = $80 >> (x AND 7)

2 bits:   (y/8)*rowbytes + (x/4)*8 + (y AND 7)
          bits 7-6 hold the pixel where x AND 3 = 0

FCM:      (y/8)*rowbytes + (x/8)*64 + (y AND 7)*8 + (x AND 7)

NCM:      (y/8)*rowbytes + (x/16)*64 + (y AND 7)*8 + (x AND 15)/2
          low nybble for even x, high nybble for odd x

Bitplanes use the same cell order as the C64 bitmap: the address of a 320-wide bitplane byte is INT(Y/8)*320 + (Y AND 7) + INT(X/8)*8 plus the plane's start (MEGA65 blog). At 640 wide, rowbytes doubles. The 400-line interlaced modes split even and odd lines between two plane addresses and are not covered here.

A "quilt" is a SEAM screen whose screen memory is filled row by row with ascending character values, as in Dan Sanderson's full-screen FCM example, so that the character data forms a bitmap in cell order (Dan Sanderson). For FCM or NCM data at $40000, the screen values run from $1000 upward; for a monochrome quilt, they run upward from the character at CHARPTR.

; plotbp: plot colour in pcol on nplanes bitplanes
; planes: table of 4-byte plane addresses
plotbp  lda pcol
        sta cbits
        lda #0
        sta plane
bploop  lda plane
        asl
        asl
        tay             ; 4 bytes per table entry
        ldx #0
copy    lda planes,y
        sta bmbase,x
        iny
        inx
        cpx #4
        bne copy
        lda cbits
        and #1

        inc plane
        lda plane
        cmp #nplanes
        bne bploop

Drawing lines

The line routine is Bresenham's algorithm in its all-octant form. It works in whole pixels for any slope, calls the plot routine whose address is in plotvec for each point, and draws both end points. x0, y0, x1, y1, dx, dy, err and e2 are 16-bit base-page variables; sx and sy are single bytes holding 1 or -1. Coordinates on the MEGA65 are small enough that no intermediate value can overflow 16 bits, so the signed comparisons test N alone.

; line: draw from (x0,y0) to (x1,y1) with the routine in plotvec
line    sec             ; dx = |x1 - x0|, sx = direction
        lda x1
        sbc x0
        sta dx
        lda x1+1
        sbc x0+1
        sta dx+1
        lda #1
        sta sx
        bit dx+1
        bpl dxok
        lda #$ff
        sta sx
        sec             ; dx = -dx
        lda #0
        sbc dx
        sta dx
        lda #0
        sbc dx+1
        sta dx+1
dxok    sec             ; dy = -|y1 - y0|, sy = direction
        lda y1
        sbc y0
        sta dy
        lda y1+1
        sbc y0+1
        sta dy+1
        lda #$ff
        sta sy
        bit dy+1
        bmi dyok        ; y1 < y0: dy is already negative
        lda #1
        sta sy
        sec             ; dy = -dy
        lda #0
        sbc dy
        sta dy
        lda #0
        sbc dy+1
        sta dy+1
dyok    clc             ; err = dx + dy
        lda dx
        adc dy
        sta err
        lda dx+1
        adc dy+1
        sta err+1

loop    lda x0          ; plot (x0, y0)
        sta px
        lda x0+1
        sta px+1
        lda y0
        sta py
        jsr plot
        lda x0          ; done when (x0, y0) = (x1, y1)
        cmp x1
        bne step
        lda x0+1
        cmp x1+1
        bne step
        lda y0
        cmp y1
        bne step
        lda y0+1
        cmp y1+1
        bne step
        rts

step    lda err         ; e2 = 2 * err
        asl
        sta e2
        lda err+1
        rol
        sta e2+1
        sec             ; if e2 >= dy: err += dy, x0 += sx
        lda e2
        sbc dy
        lda e2+1
        sbc dy+1
        bmi noxstep
        clc
        lda err
        adc dy
        sta err
        lda err+1
        adc dy+1
        sta err+1
        lda sx
        bmi xdec
        inw x0
        bra noxstep
xdec    dew x0
noxstep sec             ; if e2 <= dx: err += dx, y0 += sy
        lda dx
        sbc e2
        lda dx+1
        sbc e2+1
        bmi loop
        clc
        lda err
        adc dx
        sta err
        lda err+1
        adc dx+1
        sta err+1
        lda sy
        bmi ydec
        inw y0
        bra loop
ydec    dew y0
        bra loop

plot    jmp (plotvec)

INW and DEW step the coordinates in one instruction each, which is why the line variables live in the base page.

Using the routines

Select a mode by setting bmbase, rowbytes and plotvec, then draw:

        lda #<plotfcm
        sta plotvec
        lda #>plotfcm
        sta plotvec+1
        lda #$00        ; bmbase = $00040000
        sta bmbase
        sta bmbase+1
        sta bmbase+3
        lda #$04
        sta bmbase+2
        lda #<2560      ; 40 FCM characters x 64 bytes
        sta rowbytes
        lda #>2560
        sta rowbytes+1
        lda #5
        sta pcol        ; palette entry 5
        ; set x0, y0, x1, y1 ...
        jsr line

The plot routines change A, X, Y and Z, since Q includes all four, so a caller must not expect any register to survive. They also leave the hardware multiplier holding their last result, which matters only to code that uses the multiplier itself from an interrupt.

Summary

  • BASIC 65 draws on bitplane screens in banks 4 and 5 with SCREEN, PEN, LINE, CIRCLE and related commands, and reaches the registers directly with SETBIT, CLRBIT, WPOKE and WPEEK.
  • Pointers replace the VIC-II's banking: SCRNPTR, COLPTR, CHARPTR and the sprite pointer address can point almost anywhere, while CHRCOUNT and LINESTEP set how many characters are drawn and how far apart rows are.
  • Hot registers $D011, $D016, $D018, $D031 and $DD00 overwrite the VIC-IV pointers when written; clear HOTREG, bit 7 of $D05D, to take full control.
  • Screen size is not fixed: TBDRPOS, BBDRPOS, TEXTYPOS, TEXTXPOS, SDBDRWD, DISPROWS, CHRCOUNT and LINESTEP give custom sizes such as 88 × 30 in PAL, and CHRXSCL at $D05A scales text pixels horizontally. The screen editor knows only its four standard sizes.
  • SEAM, enabled by CHR16, gives two bytes per character, 8,192 characters, and access to FCM and NCM. LINESTEP must be at least twice CHRCOUNT. A screen word of $FFFF ends the row, and the next row starts right after it.
  • FCM stores one byte per pixel; screen memory holds the data address divided by 64. NCM is a per-character option for SEAM characters, with four bits per pixel, 16-pixel-wide characters and sub-palettes of 16. Clear ATTR when using FCM or NCM.
  • Palettes have 256 nybble-swapped entries at $D100-$D3FF, in four banks: text and bitplanes share one, sprites can use another, and characters can switch to an alternate.
  • Sprites gain 16-colour, 64-pixel-wide, variable-height and high-resolution modes, and a movable pointer list at $D06C-$D06E.
  • Bitplanes give up to 256 colours at 320 or 640 pixels wide, at a high memory cost.
  • The Raster Rewrite Buffer uses GOTOX entries to place characters at any X position and layer them with transparency, for many-object and parallax graphics. It has about 2,590 cycles of an 81 MHz clock per PAL line, one per pixel drawn plus fetching, so the busiest row sets the limit; DBLRR doubles it.
  • RRB objects are software sprites: a slot of GOTOX and glyph entries per object per row, images stored as strips of consecutive FCM glyphs with blanks at each end, and the GOTOX Y offset for pixel-exact vertical placement. The VIC-IV cannot scale single characters; CHRXSCL and CHRYSCL scale the whole display, and DMA fractional steps resample an object's image.
