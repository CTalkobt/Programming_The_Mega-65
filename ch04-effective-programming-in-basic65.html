Programming the MEGA65 — Chapter 4: Effective Programming in BASIC 65

Oct 4, 2026 · Updated Oct 19, 2026 · @Craig Taylor

Introduction

Chapter 3 described each keyword. This chapter is about putting them together: how to write BASIC 65 programs that are easy to read, easy to change, quick to debug and fast enough. Much C64 BASIC was written as a tangle of GOTOs, because C64 BASIC offered little else. BASIC 65 has proper loops, multi-line blocks, error trapping and editing tools, and a program that uses them is both shorter and far easier to work on.

The chapter covers:

  • How to become fluent in BASIC 65, and the tools that make writing programs quicker
  • The kinds of program you might write, and who will use them
  • Designing a program, from the problem to working code
  • Habits that make a program easy to use, change and trust
  • Debugging with HELP, STOP, TRON and TRAP
  • Worked examples of input, output, calculation, strings, sorting, data structures and dates
  • Making BASIC 65 run faster

Every example program in this chapter was run in the Xemu emulator with BASIC 65 ROM 920418. Where a result is shown, it is the result Xemu printed.

How to Become Fluent in BASIC 65

BASIC is a language, and like any language it is learned by reading and writing it, not only by studying its vocabulary. Chapter 3 is the vocabulary. Fluency comes from using it.

Start small

Begin with a handful of keywords, such as PRINT, INPUT, IF, FOR, DO and GOSUB, and write short programs that do one thing. Add new keywords as a program needs them. Some keywords you may never need, just as there are words in any language that you never use.

Experiment in direct mode

Any statement typed without a line number runs at once, so trying an idea costs nothing. Before writing a line into a program, try the expression on its own:

PRINT INSTR("JANFEBMAR", "FEB")
 4
PRINT USING "#####.##"; 12.257
   12.26

After an error, HELP lists the line and highlights the statement that failed (MEGA65 Book, p. B-131). Keep experiments away from programs that matter: save the program first, or work on a copy.

Read other programs

The examples in Chapter 3 and in the MEGA65 Book are short and each shows one idea. Longer programs show how the ideas fit together. LIST any BASIC program you load, including those shared by other owners on the MEGA65 Filehost, and work out how it does what it does. Borrow the techniques you like, and try a second way of solving the same problem: there is rarely only one.

Writing and editing efficiently

BASIC 65 has editing commands that earlier Commodore BASICs lacked. Used together, they make typing in and reshaping a program much quicker.

Task Command
Number lines automatically while typing AUTO 10; AUTO alone turns it off
Make room between lines, or tidy numbering RENUMBER 100, 10
List part of a program LIST 500-, LIST -70, LIST 240-350; P pauses each screenful
Find every use of a variable or word FIND "HS" for a variable; FIND /PRINT/ for a keyword
Rename a variable throughout CHANGE "XX$" TO "UU$"
Delete a block of lines DELETE 240-350
Add a library of subroutines MERGE "LIBRARY"
Keep common commands on function keys KEY 2, "DIR" + CHR$(13)
Bring in a program written on a PC IMPORT "PROGRAM" from a SEQ text file

RENUMBER updates every GOTO, GOSUB and similar reference to the lines it moves. It cannot fix line numbers a program calculates, as with FGOTO and FGOSUB, and it uses banks 4 and 5 as working space (MEGA65 Book, FGOTO, FGOSUB and MEM). With quotes, FIND and CHANGE search plain text, which finds variable names but not keywords: a keyword is stored as a token, so search for it between other delimiters, as in FIND /PRINT/. CHANGE shows each match and asks Y, N or * (all) before replacing it; answering * changes every later match too, so give it a string that cannot also appear inside a longer name: changing A would also change AB.

Saving often

DSAVE "@NAME" overwrites the previous version in one step. For bigger changes, save under a new name first, such as "GAME2", so there is always a working version to go back to. The Freezer's freeze slots can also capture the whole machine, program and all, at any moment.

Programs, Systems, and People

Before designing a program, it helps to know what kind of program it is and who will use it. The names below matter less than the distinctions.

Kinds of program

  • Stand-alone programs hold everything they need, such as their graphics, sounds and data, in one file. Most games and small utilities are like this, and they are the easiest to write and share.
  • Program systems are several programs that share data files on a disk: one program adds records to a file, another searches it, a third prints reports. Each part is simpler than one large program would be, but the parts must agree on the layout of every file, and each must check the data it reads, since another program wrote it.
  • Families of programs share a design but not their data: a set of quizzes, or levels of a game, each in its own file and each built from the same template. Once the template works, each new member is quick to write.

A program system needs a way to move from one program to the next. RUN "NAME" loads and runs another program but clears all variables first (MEGA65 Book, p. B-229). DLOAD in a running program replaces the program and starts the new one at its first line, keeping the variables, arrays and strings, so the programs can pass values to each other (MEGA65 Book, p. B-74). Files on disk are the other way to pass data, and the only way that survives switching the machine off.

Who will use the program

A program written for yourself can assume you know how to use it. One written for anyone else cannot, and a MEGA65 program shared with other owners meets a range of machines and people:

  • Different ROM versions. BASIC 65 is still being developed, and a keyword or behaviour your program relies on may be missing or different in an older ROM. FRE(-1) returns the ROM version as a six-digit number (MEGA65 Book, p. B-117), so a program can check it and warn the user. Chapter 11 explains version checks in more detail.
  • Different disk setups. The program may be run from the internal drive, an SD card disk image or a second unit. A program that keeps its unit number in one variable, rather than writing U8 everywhere, adapts easily.
  • Users who do not program. They need prompts that say what to type, menus instead of commands, and messages instead of BASIC errors. The section on Serious and Less Serious Programming covers these.

Program Design

Experienced programmers plan small programs almost without noticing. Larger ones need the planning written down. This section shows the steps for a single program and then for a system. Many working programs are untidy, and that is not a disaster, but a little planning makes a program much easier to finish and to change.

Designing a program

Take a number guessing game as an example. The computer thinks of a number from 1 to 99, and the player guesses until they find it. After a wrong guess, the computer says whether the guess was too small or too large; after the right one, it says how many guesses it took.

Writing it takes four steps, whether they are written down or done in your head:

  1. Understand the problem. This one is simple. Many are not, and a program cannot be clearer than its author's idea of what it should do.
  2. Express it in a way a computer can follow. An outline in plain English is usually enough: choose X; set the count to 0; repeat: get a guess, add 1 to the count, say whether it was too small or too large; until the guess is X; print the count. Flow charts show the same thing as boxes and arrows, but are slow to draw and to change.
  3. Write it in BASIC. With DO ... LOOP, the outline turns into BASIC 65 almost line for line. A larger program is written and tested a part at a time, each part as a subroutine.
  4. Test it and improve it.
10 SCNCLR : PRINT "GUESS MY NUMBER (1-99)"
20 X = INT(RND(0) * 99) + 1 : N = 0
30 DO
40 INPUT "YOUR GUESS"; G : N = N + 1
50 IF G < X THEN PRINT "TOO SMALL"
60 IF G > X THEN PRINT "TOO LARGE"
70 LOOP UNTIL G = X
80 PRINT "GOT IT IN"; N; "TRIES"
GUESS MY NUMBER (1-99)
YOUR GUESS? 50
TOO LARGE
YOUR GUESS? 25
TOO SMALL
YOUR GUESS? 37
GOT IT IN 3 TRIES

Testing shows what to improve. A guess of 150 or 2.5 is counted as a guess, and the game ends after one round. This version rejects guesses outside the range, and offers another game:

10 DO
20 SCNCLR : PRINT "GUESS MY NUMBER (1-99)"
30 X = INT(RND(0) * 99) + 1 : N = 0
40 DO
50 INPUT "YOUR GUESS"; G
60 IF G < 1 OR G > 99 OR G <> INT(G) THEN PRINT "1 TO 99, PLEASE" : ELSE BEGIN
70 N = N + 1
80 IF G < X THEN PRINT "TOO SMALL"
90 IF G > X THEN PRINT "TOO LARGE"
100 BEND
110 LOOP UNTIL G = X
120 PRINT "GOT IT IN"; N; "TRIES"
130 PRINT "PLAY AGAIN (Y/N)?"
140 GETKEY A$
150 LOOP WHILE A$ = "Y"

RND(0) seeds from the system clock, so each game has a different number (MEGA65 Book, p. B-218). To test with the same number every time, seed with a negative number first, such as X = RND(-1), and use RND(1) afterwards. For numbers that no seed can repeat, release 0.96 and later cores also have a hardware random number generator: PEEK($D7EF) returns a random byte from 0 to 255 (mega65-core, gs4510.vhdl). Chapter 3's RND entry shows how to roll a die with it.

Structured programming

BASIC 65 has the statements that make a program's structure visible in its listing. Using them consistently is most of what program design means in practice.

Loops without GOTO

A C64 program that waits for a key typically reads like this:

10 GET A$ : IF A$ = "" THEN 10

It works, but every such line adds a jump to follow when reading the program. BASIC 65's DO ... LOOP says what it means and needs no line number:

10 DO : GET A$ : LOOP UNTIL A$ <> ""

The condition can go at either end. With WHILE or UNTIL after DO, it is tested before each pass, so the body may never run; after LOOP, it is tested after each pass, so the body always runs at least once. A DO ... LOOP with no condition repeats until an EXIT, which suits loops whose stopping point is in the middle:

10 DO
20 INPUT "COMMAND (Q TO QUIT)"; C$
30 IF C$ = "Q" THEN EXIT
40 GOSUB 1000 : REM PROCESS THE COMMAND
50 LOOP
60 PRINT "BYE"

Use FOR ... NEXT when the number of passes is known in advance, and DO ... LOOP for everything else.

Blocks with BEGIN and BEND

On the C64, everything after THEN had to fit on one line, so longer actions meant jumping elsewhere. BEGIN and BEND let THEN and ELSE control a block of any length:

100 IF SC > HI THEN BEGIN
110 HI = SC
120 PRINT "NEW HIGH SCORE!"
130 SOUND 1, 7382, 30
140 BEND : ELSE PRINT "SCORE:"; SC

The Book notes a quirk: statements after BEND on the same line belong to the block's control flow, so keep anything that must always run on a separate line (MEGA65 Book, p. B-28).

Subroutines

GOSUB and RETURN remain the way to break a program into pieces. A few habits make subroutines easy to work with:

  • Give each a fixed home, such as 1000 for input, 2000 for drawing and 3000 for disk access, and a REM line stating what it expects and returns.
  • Pass values in agreed variables, such as X and Y for a position, since BASIC subroutines have no parameters.
  • Jump over them at the end of the main program with END or GOTO, so execution never falls into a subroutine by accident.

ON ... GOSUB and FGOSUB select a subroutine by number, which replaces chains of IF statements:

10 GETKEY K$ : K = INSTR("WASD", K$)
20 IF K THEN ON K GOSUB 1000, 1100, 1200, 1300
30 GOTO 10

Functions

DEF FN defines a one-line numeric function, which keeps a repeated formula in one place:

10 DEF FN RN(X) = INT(RND(0) * X) + 1 : REM RANDOM 1 TO X
20 PRINT FN RN(6), FN RN(100)

Data in DATA statements

Tables of fixed values belong in DATA statements rather than in long chains of assignments. READ them into arrays at the start of the program, and use RESTORE with a line number to re-read a particular table. This keeps the logic of the program separate from its data, so changing a level layout or a list of prices does not touch the code.

Designing a system

A program system, such as a club membership list with programs to add, search and print members, needs three more steps before any code is written.

Ask whether it is feasible. Estimate how much data there will be and where it will live. In Xemu with ROM 920418, a new program has about 55,000 bytes free for its own lines and another 55,000 for variables, which FRE(0) and FRE(1) report (MEGA65 Book, p. B-117). More data than that must stay in disk files and be read a record at a time. Estimate the speed too: a search through a few hundred records in memory is quick, but reading them from disk for every search may not be. If in doubt, write a short test program that does the slowest part, and time it with TI.

Write a solution in outline. Decide the files first: what each record holds, in what order, and how the end of the file is marked. Then decide which program reads and writes each file.

Write the programs in modules. Each module is a subroutine with one way in and one way out, so it can be tested on its own and changed without breaking the others. Where a decision depends on several conditions, a condition table is easier to check than a chain of IF statements. Each column is one case; the actions marked X are taken when its conditions hold. This one decides what to do with a new score and a high-score table:

1 2 3
Table full? N Y Y
Score above the lowest in the table? – Y N
Remove the lowest score X
Insert the new score in order X X
Say “no high score” X

A table makes it easy to see that every case is covered, and each column becomes one branch of the code.

Serious and Less Serious Programming

There is no single right way to write a program. A game for yourself can be as informal as you like. A program others will use, or one you will come back to in a year, repays some care. This section lists the things worth thinking about.

Conventions

BASIC 65 tolerates spaces, and using them costs only a little memory. A few conventions make listings readable:

  • One statement per line where practical, except for short, closely related ones.
  • REM lines to head each section and each subroutine. Do not put a REM on a line that GOTO or GOSUB jumps to, so it can be deleted later without breaking the jump.
  • Line numbers in steps of 10, with each major section starting on a round hundred or thousand. Keep a standard subroutine at the same line number in every program, so it can be MERGEd without clashes.
  • Short variable names, chosen so that they do not contain keywords: TOTAL contains TO, and SCORE contains OR, and both cause syntax errors. Only the first two characters count, so COUNT and CO are the same variable.
  • A convention for working variables. All BASIC variables are global, so a subroutine that uses I as a loop counter will change the I of a loop that calls it. Reserve some names, such as those ending in 9, for use inside subroutines only.

Documentation

REM lines at the head of a subroutine are its documentation: what it does, which variables it reads, which it sets and which it uses for working. A program for other people also needs instructions, either on screen or in a text file on the same disk, that say how to start it, what each option does and what files it needs.

Ease of change

A value written directly into the code, such as a unit number or the size of a table, is hard-coded; a value kept in a variable set at the start is soft-coded. Soft-coded programs are easier to change, and in BASIC 65 they are also faster, because a number written in the program text is converted from its characters every time the line runs, while a variable already holds the value (see Keep constants in variables):

10 DV = 8 : MX = 100 : REM DISK UNIT, MOST RECORDS
...
500 DOPEN#1, "MEMBERS", U(DV)

A program can go further and ask for its settings at the start, or read them from a small file.

Error messages

A message to the user should say what was wrong and what to do about it. Showing messages in the same place, the same way, makes them easy to notice. This subroutine shows the text in EM$ in reverse on the bottom line for three seconds, then clears it:

9000 REM SHOW EM$ ON THE BOTTOM LINE
9010 CURSOR 0, 24 : PRINT CHR$(18); EM$; CHR$(146);
9020 SLEEP 3
9030 CURSOR 0, 24 : PRINT SPC(LEN(EM$));
9040 RETURN

Call it with EM$ = "NAME TOO LONG" : GOSUB 9000. CHR$(18) and CHR$(146) turn reverse on and off, and SLEEP waits the given number of seconds (MEGA65 Book, p. B-242).

Easy input

INPUT is fine for many programs, but it lets the user type anything, and a letter typed where a number is expected gives a ?REDO FROM START. A prompt that says what to type, and what form it takes, prevents most mistakes:

100 PRINT "ENTER THE DISCOUNT PERCENTAGE"
110 INPUT "(FOR EXAMPLE 13.25)"; PC

For full control, read the keys one at a time with GETKEY and accept only the ones that make sense; Input, under Examples in BASIC 65, shows a routine that does this.

Menus

A menu lets the user pick an action with a single key. GETKEY waits for the key, INSTR turns it into a number, and ON ... GOSUB runs the matching subroutine:

100 DO
110 PRINT "1 NEW GAME  2 HIGH SCORES  Q QUIT"
120 GETKEY K$ : K = INSTR("12Q", K$)
130 IF K = 3 THEN EXIT
140 ON K GOSUB 1000, 2000
150 LOOP

A key that is not in the list gives K = 0, and ON ... GOSUB with 0 does nothing, so the menu simply waits again. If each option is a separate program, the menu can load it with DLOAD, keeping the variables, as described under Kinds of program.

Tidy output

Columns of numbers are easier to read when they line up. PRINT USING formats a number to a fixed width and number of decimal places, so there is no need for the string-handling routines older BASICs needed; Output, under Examples in BASIC 65, shows it.

Libraries of subroutines

Subroutines that are useful in many programs, such as the input routine and the message routine above, can be kept in one program file and added to a new program with MERGE. Give the library high line numbers and its own variable names, so it does not clash with the programs that use it.

Before writing a library routine, check whether BASIC 65 already has it. Many routines that C64 programmers wrote for themselves are built-in keywords: HEX$ and DEC convert between hexadecimal and decimal (MEGA65 Book, pp. B-132, B-66), PRINT USING formats numbers, MOD gives remainders, INSTR searches strings, and MID$ can replace part of a string.

Testing

Testing every possible input is rarely possible, so test the ones most likely to fail:

  • Boundary values, such as 0, 1, the largest value allowed and one more than that, negative numbers and fractions.
  • Empty and awkward input, such as just pressing RETURN, a very long string, or a comma or quotation mark, which INPUT treats specially.
  • Generated data. A loop can feed a routine a range of values, and RND can make up random ones. Seed RND with a negative number so that the same test data comes back on every run (MEGA65 Book, p. B-218).

It is hard to test your own program fairly, because you avoid the mistakes you know it cannot handle. Ask someone else to try it.

Validation

Validation checks that data has the right form before the program uses it: a month between 1 and 12, a name that is not empty, a number that is a whole number. It cannot tell whether the data is right, only whether it could be.

A check digit catches most typing mistakes in a reference number. The old ten-digit ISBN is an example: multiply the first nine digits by 1 to 9, add the results, and the remainder after dividing by 11 is the tenth digit, with X standing for 10. A single wrong digit, or two neighbouring digits swapped, gives a different check digit:

10 I$ = "030640615" : S = 0
20 FOR J = 1 TO 9 : S = S + J * VAL(MID$(I$, J, 1)) : NEXT
30 C = MOD(S, 11) : C$ = MID$("0123456789X", C + 1, 1)
40 PRINT I$ + C$
0306406152

Robust programs

A program used by other people meets input and situations its author did not expect. Four habits deal with most of them:

  • Validate input. Check that a number is in range and a string is not empty before using it, and ask again if not.
  • Check every disk operation. Test DS after DOPEN, DLOAD and similar commands, and show DS$ if it is not zero.
  • Trap the rest. A TRAP handler that reports the problem and returns to a safe point, such as the main menu, is better than a program that stops with an error.
  • Leave the machine as you found it. Restore BANK 128, the palette, the screen mode and SPEED before the program ends, and close every file.

This input routine combines several of them:

1000 REM INPUT A NUMBER FROM LO TO HI INTO N
1010 DO
1020 INPUT "NUMBER"; N$
1030 N = VAL(N$)
1040 LOOP UNTIL N >= LO AND N <= HI AND N$ <> ""
1050 RETURN

Reading the input as a string and converting it with VAL means a typed letter never produces a REDO FROM START message or stops the program.

Debugging BASIC 65 Programs

Errors come in three kinds:

  • Syntax errors are lines BASIC cannot understand. BASIC reports them when the line runs, not when it is typed, so a mistake in a rarely used branch can wait a long time to appear.
  • Run-time errors are lines that are correct BASIC but are given values they cannot handle, such as a division by zero or an array index out of range. Error Handling in Chapter 3 lists every error and its cause.
  • Logic errors give no message at all: the program runs, but does the wrong thing. These are the hardest to find, and most of this section is about them.

Read the message

When BASIC stops with an error, it names the error and the line. HELP then lists that line and highlights the statement that failed, which matters on long lines with several statements (MEGA65 Book, p. B-131).

Inspect variables

After a program stops, its variables keep their values. PRINT them in direct mode, change them if needed, and continue with CONT, provided no program line has been edited in the meantime and the program did not stop with an error. A STOP placed in the program acts as a breakpoint:

200 IF X > 319 THEN PRINT "X OUT OF RANGE:"; X : STOP

Trace execution

TRON prints each line number as it runs, and TROFF turns it off. Tracing a whole program produces a flood of numbers, so turn it on just before the suspect section and off just after:

500 TRON
510 GOSUB 2000
520 TROFF

Catch errors

TRAP sends errors to a handler line instead of stopping the program, and ER, EL and ERR$(ER) say what went wrong and where. During development, a handler that prints this information and then stops is more useful than letting errors pass silently:

10 TRAP 9000
...
9000 PRINT ERR$(ER); " IN LINE"; EL : STOP

Catching errors in a program in Chapter 3 explains how TRAP and RESUME work together, and Chapter 6 shows fuller error handling.

Common mistakes

Symptom Likely cause
?SYNTAX ERROR in a line that looks correct A keyword hidden inside a variable name
A variable is unexpectedly zero It is misspelled
Two variables seem to change each other Their names share the first two characters, so BASIC treats them as one variable
A loop ends early, or never ends A subroutine it calls uses the same loop variable
A function gives 0, or ?BAD SUBSCRIPT FN was left out, so RN(6) is read as an element of the array RN
The program runs into the wrong code A subroutine lacks its RETURN, or the main program lacks an END before the subroutines
?OUT OF DATA, or data read in the wrong order A READ loop runs further than the DATA, a RESTORE is missing, or DATA lines were given the wrong numbers
A condition is true when it should be false Missing parentheses around a comparison combined with AND or OR; see Precedence in Chapter 3
A negative number rounds the wrong way INT, and assignment to an integer variable, round down, so -1.5 becomes -2, not -1
A disk command fails without an error DS was not checked; print DS$
POKEs to $D020 or similar do nothing BANK is not 128
A program behaves differently after editing It was restarted with GOTO, which keeps the old variable values (editing does not clear them); use RUN

Some behaviour differs from C64 BASIC and can surprise a C64 programmer. ASC("") returns 0 instead of raising an error (MEGA65 Book, p. B-21). MOD with a positive divisor is never negative: MOD(-17, 5) is 3, not -2. And RND starts from a different seed each time the machine is switched on, so a program that relied on the C64's repeatable sequence must seed RND itself (MEGA65 Book, p. B-218).

Examples in BASIC 65

The examples below show common programming tasks in BASIC 65. They are short enough to type in, and each is a starting point to change and extend.

Input

This subroutine reads up to ML characters into IN$, accepting only the characters listed in OK$. DEL removes the last character, and RETURN ends the input. Any other key is ignored, so the user cannot move the cursor about the screen or type a letter into a number:

10 OK$ = "0123456789" : ML = 5
20 GOSUB 1000 : PRINT : PRINT "YOU TYPED"; VAL(IN$)
30 END
1000 REM READ UP TO ML CHARACTERS FROM OK$ INTO IN$
1010 IN$ = ""
1020 DO
1030 GETKEY K$
1040 IF K$ = CHR$(13) THEN EXIT
1050 IF K$ = CHR$(20) AND IN$ <> "" THEN IN$ = LEFT$(IN$, LEN(IN$) - 1) : PRINT K$;
1060 IF INSTR(OK$, K$) > 0 AND LEN(IN$) < ML THEN IN$ = IN$ + K$ : PRINT K$;
1070 LOOP
1080 RETURN

Typing 1, 2, A, 3, DEL, 4, 5 and RETURN gives 1245: the A is ignored and DEL removes the 3. For a name, set OK$ to the letters and a space; for a decimal number, add a full stop to OK$ and check that IN$ holds only one.

Output

PRINT USING prints a value to a pattern. Each # is one character position, and a full stop in a numeric pattern places the decimal point, rounding the value to fit (MEGA65 Book, p. B-200). A string printed with a pattern is cut or padded to its width, so names and prices line up in columns:

10 FOR I = 1 TO 3 : READ D$, P
20 PRINT USING "############"; D$;
30 PRINT USING "#####.##"; P : NEXT
40 DATA "COFFEE", 3.5, "CAKE", 12.257, "TEA", 1234.5
COFFEE          3.50
CAKE           12.26
TEA          1234.50

PRINT USING also takes C-style patterns, such as "%5D" for a whole number five characters wide and "%4X" for four hexadecimal digits. Unlike C, the width of "%7.2F" does not count the decimal point: it gives five positions before the point and two after, eight characters in all, the same as "#####.##". A value too large for its pattern is printed as asterisks, except in a %X pattern, which keeps only the last digits. Chapter 3 lists all the patterns.

Calculations

To round a number to two decimal places for later use, rather than just for printing, multiply, add a half, take INT and divide:

10 X = 2.675 : PRINT INT(X * 100 + .5) / 100
 2.68

MOD gives the remainder of a division (MEGA65 Book, p. B-169). It is the way to wrap a value around, such as a position on a circular track or an hour on a clock, and to test whether one number divides another: IF MOD(Y, 4) = 0. HEX$ and DEC convert to and from hexadecimal:

PRINT DEC("ABCD"), HEX$(43981)
 43981    ABCD

String handling

These lines reverse a string, count its words and replace part of it. INSTR takes an optional starting position, so a loop can find each space in turn (MEGA65 Book, p. B-141). MID$ used as a statement replaces characters in a string variable without changing its length (MEGA65 Book, p. B-167):

10 A$ = "PROGRAMMING THE MEGA65"
20 R$ = "" : FOR I = LEN(A$) TO 1 STEP -1 : R$ = R$ + MID$(A$, I, 1) : NEXT : PRINT R$
30 W = 0 : P = 1
40 DO : P = INSTR(A$, " ", P) : IF P = 0 THEN EXIT
50 W = W + 1 : P = P + 1 : LOOP
60 PRINT W + 1; "WORDS"
70 MID$(A$, 13, 3) = "OUR" : PRINT A$
80 PRINT INSTR(A$, "MEGA")
56AGEM EHT GNIMMARGORP
 3 WORDS
PROGRAMMING OUR MEGA65

Sorting, searching and shuffling

This program fills an array with the numbers 1 to 10, shuffles them, sorts them again and then searches for one. The shuffle swaps each element with a randomly chosen one at or below it, which gives every order the same chance. The sort is an insertion sort: each element in turn moves down past the larger elements before it. It is simple and quick for a few hundred items, and quickest of all when the data is already nearly in order. The search is a binary search, which halves the part of a sorted array still to be searched at each step, so it needs at most seven steps for a hundred items:

10 N = 10 : DIM A(N) : X = RND(-7)
20 FOR I = 1 TO N : A(I) = I : NEXT
30 FOR I = N TO 2 STEP -1
40 J = INT(RND(1) * I) + 1
50 T = A(I) : A(I) = A(J) : A(J) = T
60 NEXT
70 FOR I = 1 TO N : PRINT A(I); : NEXT : PRINT
100 FOR I = 2 TO N
110 T = A(I) : J = I - 1
120 DO WHILE J > 0
130 IF A(J) <= T THEN EXIT
140 A(J + 1) = A(J) : J = J - 1
150 LOOP
160 A(J + 1) = T
170 NEXT
180 FOR I = 1 TO N : PRINT A(I); : NEXT : PRINT
200 K = 7 : LO = 1 : HI = N : F = 0
210 DO WHILE LO <= HI AND F = 0

Line 10 seeds RND with -7, so the shuffle is the same on every run; use RND(0) instead for a different one each time. To sort strings, use a string array: the comparisons work the same way. F is 0 if the value is not found.

Data structures

Arrays are BASIC's only data structure, but they can be used to build others. Parallel arrays keep related values at the same index, here a name and a score. A two-dimensional array holds a grid, such as a game board. A stack is an array with a variable, SP, that points to its top item: adding an item increases SP, and taking one decreases it, so items come off in the reverse of the order they went on:

10 READ N : DIM N$(N), S(N)
20 FOR I = 1 TO N : READ N$(I), S(I) : NEXT
30 B = 1 : FOR I = 2 TO N : IF S(I) > S(B) THEN B = I
40 NEXT : PRINT "BEST: "; N$(B); S(B)
50 DATA 4, "ANN", 320, "BOB", 450, "CAL", 120, "DEE", 410
100 DIM B$(2, 2) : REM A 3 BY 3 BOARD
110 B$(1, 1) = "X" : B$(0, 2) = "O"
120 FOR R = 0 TO 2 : FOR C = 0 TO 2
130 IF B$(R, C) = "" THEN PRINT "."; : ELSE PRINT B$(R, C);
140 NEXT : PRINT : NEXT
200 DIM ST(20) : SP = 0 : REM A STACK
210 FOR I = 1 TO 3 : SP = SP + 1 : ST(SP) = I * 10 : NEXT
220 DO WHILE SP > 0 : PRINT ST(SP); : SP = SP - 1 : LOOP : PRINT
BEST: BOB 450
..O
.X.
...
 30  20  10

The first item in a DATA list, here 4, says how many records follow, so the DIM is the right size and adding a record means changing only the DATA. Arrays in Chapter 3 gives the rules for array sizes.

Processing dates

DT$ gives today's date from the real-time clock in the form DD-MMM-YYYY, such as 15-OCT-2026 (MEGA65 Book, p. B-87). This program splits such a date into numbers, finds the day of the week and counts the days to Christmas:

10 D$ = "15-OCT-2026" : REM OR D$ = DT$
20 D = VAL(LEFT$(D$, 2))
30 M = (INSTR("JANFEBMARAPRMAYJUNJULAUGSEPOCTNOVDEC", MID$(D$, 4, 3)) + 2) / 3
40 Y = VAL(RIGHT$(D$, 4))
50 PRINT D; M; Y
60 GOSUB 1000 : PRINT MID$("SUNMONTUEWEDTHUFRISAT", W * 3 + 1, 3)
70 GOSUB 2000 : N1 = DN
80 D = 25 : M = 12 : Y = 2026 : GOSUB 2000
90 PRINT DN - N1; "DAYS TO CHRISTMAS"
100 END
1000 REM DAY OF WEEK W (0 = SUNDAY) OF D, M, Y
1010 Y1 = Y : IF M < 3 THEN Y1 = Y - 1
1020 W = MOD(Y1 + INT(Y1/4) - INT(Y1/100) + INT(Y1/400) + VAL(MID$("032503514624", M, 1)) + D, 7)
1030 RETURN
2000 REM DAY NUMBER DN OF D, M, Y
2010 Y1 = Y : M1 = M : IF M1 < 3 THEN Y1 = Y1 - 1 : M1 = M1 + 12
2020 DN = 365 * Y1 + INT(Y1/4) - INT(Y1/100) + INT(Y1/400) + INT(153 * (M1 - 3) / 5 + .4) + D
2030 RETURN

The subroutine at 2000 turns a date into a count of days, so the difference between two counts is the number of days between them. Both subroutines follow the Gregorian calendar's leap-year rule, and they also give the right day for 1 January 2000 (Saturday) and 29 February 2024 (Thursday). A date stored as YYYYMMDD, such as 20261015, sorts into date order as a plain number or string, which DD-MMM-YYYY does not.

Making BASIC 65 Run Faster

MEGA65 mode runs at 40.5 MHz, so BASIC 65 is already far faster than C64 BASIC. When more speed is needed, these techniques help, roughly in order of effect.

Measure first

TI is a timer with microsecond resolution, restarted by CLR TI. Time the part of the program in question before and after a change, rather than guessing:

10 CLR TI
20 FOR I = 1 TO 10000 : X = X + 1 : NEXT
30 PRINT TI; "SECONDS"

The table shows how long some loops of 2,000 passes took in Xemu with ROM 920418, at 40.5 MHz. Real hardware gives different times, so treat them as a comparison between the lines, not as absolute speeds:

Loop body Seconds
X = X + 1 0.21
XX = XX + 1 0.26
ZZ = ZZ + 1, created after ten other variables 0.32
X% = X% + 1 0.24
X = X + 1 : REM A LONG COMMENT INSIDE THE LOOP 0.28
X = X + 1.5 0.28
X = X + O, with O set to 1.5 before the loop 0.20
Y = SIN(I * π / 180) 0.64
Y = S(MOD(I, 360)), from a table of sines 0.43

Use fast variables

A variable whose name is a single letter, with or without a type symbol, is a fast variable: BASIC 65 finds it without searching (MEGA65 Book, p. B-7). Give the variables used in the busiest loops one-letter names, such as I, X, Y and C$. Other variables are found by searching them in the order they were created, so a two-letter variable created late is slower still, as the ZZ line shows. Create the busiest ones first, for example by setting them to 0 at the start of the program.

Integer variables save memory in arrays, but they do not make arithmetic faster: BASIC 65 calculates in floating point, so an integer variable is converted each time it is used, and X% is slower than X.

Keep the CPU at full speed

Check that nothing has slowed the CPU: SPEED with no argument selects 40.5 MHz, and RSPEED reports the current speed. Programs that run in C64 mode can use POKE 0,65.

Move work out of loops

Calculate values that do not change before the loop starts, and use tables read from DATA instead of repeated arithmetic. A table of 360 sine values, read once, is much faster than calling SIN in every pass. A REM inside a loop is skipped on every pass, so put comments before or after the loop instead.

Keep constants in variables

When BASIC 65 stores a program line, it turns keywords into tokens but leaves numbers as the characters you typed. A 1.5 in a line is stored as the three characters 1, . and 5, and every time the line runs, the interpreter reads them one at a time and builds the number from them: multiplying by ten for each digit, noting where the decimal point falls, and checking for an exponent. A variable needs none of that. BASIC finds it, directly for a one-letter name or by searching the variable table for a longer one, and copies out a value that is already in the form it calculates with. In the timings above, X = X + O ran in 0.20 seconds against 0.28 for X = X + 1.5. Set constants used in busy loops, such as a step size or a screen width, to variables before the loop starts.

Use the commands that do the work in hardware

Several BASIC 65 commands hand work to the MEGA65's hardware or to machine code in the ROM, and one of them replaces many BASIC statements:

Instead of Use
A loop of POKEs to copy or fill memory EDMA
PEEK, AND and POKE to change one bit SETBIT and CLRBIT
Two POKEs for a 16-bit value WPOKE
A POKE loop to draw on the text screen T@& and C@&, or PRINT
Plotting shapes pixel by pixel LINE, BOX, CIRCLE, PAINT
Moving sprites every frame MOVSPR with a speed, which BASIC updates in the background

Avoid string churn

Every new string value takes fresh memory, and BASIC pauses to reclaim the old ones when memory runs low. Avoid building strings a character at a time inside fast loops, and reuse string variables rather than creating many.

Remove spaces last

Removing the spaces from a line, and joining short lines into longer ones, makes little difference: the loop above ran about 4% faster without spaces. It also makes the program much harder to read, so do it, if at all, only to a finished program, and keep the readable version.

When BASIC is not enough

If a routine is still too slow after these steps, rewrite just that routine in machine language and call it with SYS, as Chapter 9 describes. Usually only a small part of a program needs this.

Summary

  • Fluency. Start with a few keywords, experiment in direct mode, read other programs, and use AUTO, RENUMBER, FIND, CHANGE, DELETE, MERGE, KEY and IMPORT to write and reshape programs quickly.
  • Programs and people. Know whether you are writing a stand-alone program, a system or a family of programs, and who will run it, on which ROM and disk setup.
  • Design. Understand the problem, outline it, write it, then test and improve it. DO ... LOOP, BEGIN and BEND, subroutines and DEF FN give the program a visible structure; a system needs a feasibility check, file layouts and modules.
  • Care. Use conventions, document subroutines, soft-code settings, give clear messages and menus, validate input, test boundary values and leave the machine as you found it.
  • Debugging. HELP shows the failing statement; STOP and CONT inspect state; TRON and TROFF trace; TRAP catches errors.
  • Speed. Measure with TI, use one-letter variables, keep constants in variables, move work out of loops, keep the CPU at 40.5 MHz, and use EDMA, SETBIT, WPOKE, the screen arrays and graphics commands.
