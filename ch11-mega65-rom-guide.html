Programming the MEGA65 — Chapter 11: MEGA65 ROM Guide

Oct 4, 2026 · @Craig Taylor

Introduction

The MEGA65's ROM holds the KERNAL, the screen editor, BASIC 65, the DOS, the monitor, the character sets, and a complete set of C64 ROMs for C64 mode. It is the largest system ROM Commodore ever designed, and unlike the C64's it is still changing: new releases appear regularly, fixing bugs and adding features.

That makes the question "which parts can I call?" more important than it was on the C64. On a C64, programmers called almost any ROM routine they found, because the ROM never changed. On the MEGA65, a routine that is not part of an official interface may move in the next release. The MEGA65 team treats the KERNAL jump table as officially supported, along with certain documented facts about the memory layout such as $2001 being the start of BASIC (Dan Sanderson, MEGA65 Digest). Almost everything else is internal.

This chapter therefore concentrates on the stable interfaces:

  • How the ROM is organised and how to tell which version is installed
  • The KERNAL jump table, including the C65 additions
  • The RAM vectors for interrupts and I/O
  • The Hypervisor's DOS functions
  • Practices for writing code that survives ROM updates

There is no complete map of BASIC 65's internal routines here, of the kind West gave for the C64's BASIC. Such a map would be out of date within months, and code built on it would break with it. Where earlier chapters needed BASIC internals, such as the USR function's conversion routines, the safest course is to check the documentation for the ROM version in use.

ROM Layout and Versions

The ROM is a single 128KB image, loaded from the SD card into chip RAM at $20000-$3FFFF and write-protected, as Chapter 5 described. Because it is an ordinary file, the installed version is simply whichever image the SD card holds, and different machines may run different versions.

Where things are

The MEGA65 ROM inherits its overall arrangement from the C65's. The C65 brings its system ROM into the CPU's window using both banking mechanisms: $D030 for the editor at $C000, and MAP for the rest (MEGA65 ROM issue #62). The original C65 ROM boots with a mapping that implies this layout:

ROM address Seen by the CPU at Contents
$2C000-$2CFFF $C000-$CFFF, through $D030 Interface and screen editor
$32000-$37FFF $2000-$7FFF, through MAP Further system and BASIC code
$38000-$3BFFF $8000-$BFFF, through MAP BASIC
$3E000-$3FFFF $E000-$FFFF, through MAP KERNAL, including the jump table and hardware vectors

The rest of the image holds the DOS, the monitor, the character sets and the C64-mode BASIC and KERNAL. Treat this table as orientation only. The ROM's internal arrangement is not an interface, MEGA65 releases have reorganised it, and code should reach the ROM only through the jump table and vectors described in the following sections.

Identifying the version

MEGA65 ROM versions are six-digit numbers such as 920379, shown in the start-up banner. They fall into two series. The 92xxxx releases were the long-running first series; the 99xxxx releases followed with substantial changes, enough that tools written for one series do not always work with the other (Eleven IDE).

The ROM version matters most to programs that depend on behaviour added in a particular release, such as the BASIC 65 features dated in Chapter 6. Such programs should say which version they need. Programs that keep to the interfaces in this chapter rarely need to check at all.

As on every Commodore machine since the C64, the byte at $FF80 holds a KERNAL version number (pagetable.com). It distinguishes KERNAL revisions, but it is not the six-digit ROM version shown in the banner.

A program that needs the ROM version itself can call VERSIONQ at $FF2F, one of the MEGA65's own additions to the jump table (see Extended entries). It returns the ROM version in Q, the 32-bit register made up of A, X, Y and Z, as a little-endian integer, so a single STQ stores it in four bytes:

        jsr $ff2f       ; VERSIONQ
        stq version     ; four bytes, low byte first

VERSIONQ is not on the C65, so a program that might run on a C65 ROM should not rely on it.

The KERNAL Jump Table

The jump table is a list of JMP instructions at the top of the KERNAL, each at a fixed address. Programs call the fixed address, and the JMP there leads to wherever the routine currently lives. When a new ROM moves a routine, only the JMP changes.

The MEGA65-mode KERNAL derives from the C65's, which in turn derives from the C128's. Its table has two parts: the standard entries shared with the C64, and an extended block below them inherited from the C128 by way of the C65, to which the MEGA65 has added entries of its own.

Standard entries

These 39 entries occupy the same addresses as on the C64, and most do the same jobs (pagetable.com). Four addresses hold different routines on the MEGA65: KEY, MONEXIT, ScanStopKey and SCRORG take the places of the C64's SCNKEY, SETTMO, UDTIM and SCREEN. MEMTOP, MEMBOT and IOBASE are reserved. Some routines that keep their C64 names take different arguments: the clock routines work in BCD hours, minutes, seconds and tenths. PLOT keeps the C64's registers, with the line in X and the column in Y, but measures them from the top-left corner of the current window rather than of the screen. The inputs and outputs in the table come from the MEGA65 Book's KERNAL Jump Table appendix.

X/Y means a 16-bit value with the low byte in X and the high byte in Y. C is the carry flag: routines that can fail return with C=1 and an error code in A. A dash means the routine takes no input or returns no result. Unless the table says otherwise, assume a KERNAL routine changes every register and flag. All of them expect the KERNAL's normal memory map, with the base page register B set to $00.

Extended entries

The C65 kept most of the C128's additions, dropped three that made sense only on a C128 (DMA_CALL, DLCHR and GETCFG), and added MONITOR_CALL. The removals moved many entries to new addresses, so they do not match the C128 (pagetable.com). The MEGA65 has extended the table downwards: the entries from $FF2F to $FF4A are its own additions and are not on the C65.

The last six are not among the entries the C65 moved, so they keep their C128 addresses. PRIMM at $FF7D is confirmed on the MEGA65 (MEGA65 Digest). The far-memory calls do not take the same arguments as on the C128: LDA_FAR, STA_FAR and CMP_FAR take the bank in the Z register, and JSRFAR and JMPFAR take their target and register values from base page locations $02-$09. The inputs and outputs come from the MEGA65 Book's KERNAL Jump Table appendix.

Example: printing with PRIMM

PRIMM reads the bytes after the JSR as a string, prints them, and returns to the instruction after the terminating zero:

        jsr $ff7d       ; PRIMM
        .text "HELLO, MEGA65", 13, 0
        rts             ; execution continues here

It is the shortest way to print a fixed message from machine language, and it needs no pointer setup.

RAM Vectors

The jump table lets programs call the KERNAL. The RAM vectors let programs change what the KERNAL does. Each is a two-byte address in RAM that the KERNAL jumps through at a key moment, such as handling an interrupt or outputting a character. Pointing a vector at your own routine inserts that routine into the KERNAL's work.

The standard vector table

The C65's vector table at $0314-$0333 follows the C64 and C128 layout, with the vector the C64 left unused now serving the monitor (pagetable.com). The MEGA65 KERNAL inherits it from the C65.

The VECTOR call at $FF8D copies this whole table to or from memory, and RESTOR at $FF8A resets it to the defaults. Using VECTOR to save the table before changing it, and to put it back afterwards, is safer than editing individual entries.

The C65 also added vectors for the low-level serial bus routines, from $0335 upward: TALK, LISTEN, TKSA, SECOND, ACPTR, CIOUT, UNTLK and UNLSN. They are spaced three bytes apart rather than two, and they are not part of the table VECTOR copies.

Chaining into the IRQ

A cooperative program that wants code to run on every system interrupt, such as a background music player, points CINV at its own routine and ends that routine by jumping to the old handler, so that keyboard scanning and the clock keep working:

install sei
        lda $0314
        sta oldirq
        lda $0315
        sta oldirq+1
        lda #<myirq
        sta $0314
        lda #>myirq
        sta $0315
        cli
        rts

myirq   inc $d020       ; the routine's own work
        jmp (oldirq)    ; continue with the KERNAL handler

oldirq  .word 0

The KERNAL saves A, X and Y before jumping through CINV, as on the C64. Do not assume it also saves Z or B: a routine that changes them must restore them itself. Changing the vector inside SEI and CLI prevents an interrupt from arriving when only one byte has been written.

Hardware vectors

Separate from the RAM vectors are the CPU's own vectors at the top of the KERNAL ROM: NMI at $FFFA, RESET at $FFFC and IRQ/BRK at $FFFE. They point into the KERNAL, which then jumps through the RAM vectors. A takeover program that switches the KERNAL out replaces them with its own, as shown in Chapter 8.

BASIC vectors and USR

BASIC 65 has its own vectors, which belong to BASIC rather than the KERNAL. The one programs most often need is the USR vector, two bytes at $02F8, low byte first, read in the system bank: BANK 128 : WPOKE $02F8, $1800 points USR at a routine at $1800 (MEGA65 Book, p. B-285). Chapter 9 describes writing USR routines. Other BASIC vectors and work areas are internal and should not be assumed from the C64 or C128.

Hypervisor Services

The Hypervisor's services, documented by the MEGA65 Book for Hyppo version 1.2, are reached through trap registers at $D640-$D67F. The service number goes in A, other inputs in X, Y and Z, and the write is followed by CLV, because the CPU may or may not execute the byte after the trap when the service returns. On return, carry set means success; carry clear means failure, with an error code in A. Registers not used for results are preserved, and the trap registers exist only in the MEGA65 I/O personality (MEGA65 Book, pp. N-4, N-5).

Most services use $D640. A few use other trap registers: $D641 for ROM write-protection, $D642 for configuration and freeze-slot services, $D643 for serial monitor output, and $D67F for a program to freeze itself (MEGA65 Book, Appendix N).

Several services have extra requirements. setname needs the name to start on a page boundary between $0000 and $7E00, be shorter than 63 characters and end with a zero byte; it is ASCII, and Hyppo does not convert from PETSCII. Services that pass data use the transfer area, which setname also sets to the name's page. The file services work on the FAT32 file system of the SD cards, not on floppy disks or disk images (MEGA65 Book, pp. N-10, N-38).

Versions

Hyppo is updated with the MEGA65 core, independently of the ROM. In August 2026, for example, a mega65-core pull request filled in getdisksize, getcwd, mkdir, rmdir, seekfile and rename, finished fstat, and added long file name support to mkfile (mega65-core PR #946). A program should therefore call getversion first and treat error $82, not implemented, as an expected result for newer services rather than as a failure of the program.

Writing ROM-Independent Code

A MEGA65 program may be run on a ROM newer, or older, than the one it was written on. The habits below keep it working across versions.

Practice Why
Call the KERNAL only through the jump table Routine addresses move between releases; jump table addresses do not
Change KERNAL behaviour through RAM vectors, using VECTOR and RESTOR The vector table is an interface; patching ROM code is not
Avoid BASIC 65 internals BASIC's routines, work areas and token handling change from release to release
Use the Hypervisor for SD card files Its function numbers are stable and its version can be checked
Check versions only where a feature demands it Version checks for features you do not use only add ways to fail
Use a private base page, as in Chapter 9 BASIC 65 and KERNAL zero-page usage is private to the ROM
Prefer flat addressing and DMA to MAP in cooperative code The ROM's map settings are internal and cannot be read back

Zero page and system RAM

The C64's zero page was so well documented that programmers routinely borrowed its locations. On the MEGA65 that is risky. The MEGA65 team keeps what it calls a private API contract over the KERNAL's zero page, so its use can change (MEGA65 ROM issue #80). The same issue records a ROM release that began using a zero-page location in C64 mode that third-party software also used, breaking that software.

A routine that needs base page storage should therefore bring its own, by pointing B at a page it owns. A routine that must share zero page should restrict itself to locations the ROM documentation for its target version describes as free.

When a ROM routine is unavoidable

Sometimes a program genuinely needs an internal ROM routine, such as BASIC's floating-point conversion for USR. In that case:

  1. Keep every such address in one place in the source, labelled with the ROM version it was taken from.
  2. Have the program check the ROM version at start-up and refuse to run, with a clear message, on a version it was not tested with.
  3. Note the dependency in the program's documentation, so users know to look for an update after upgrading their ROM.

This turns a silent crash after a ROM update into a clear message, which is the best that can be done for code outside the official interfaces.

Summary

  • Stability. The KERNAL jump table is the officially supported ROM interface. BASIC 65 internals, ROM layout and KERNAL zero page are private and change between releases.
  • Layout and versions. The 128KB ROM lives at $20000-$3FFFF. Versions are six-digit numbers in two series, 92xxxx and 99xxxx; $FF80 holds a separate KERNAL version byte.
  • Jump table. The 39 C64 entries at $FF81-$FFF3 are unchanged. The C65-derived extended block runs from SPIN_SPOUT at $FF4D to PRIMM at $FF7D, with C128-style calls at C65 addresses and bank numbers passed in Z.
  • RAM vectors. CINV, CBINV and NMINV at $0314-$0319 and the I/O vectors up to $0333 follow the C64 layout; VECTOR and RESTOR manage them safely. Interrupt routines chained through CINV must preserve Z and B themselves.
  • Hypervisor. Even-numbered functions in A, a write to $D640, CLV, and carry for success. Hyppo 1.2 leaves directory creation, renaming, seeking and all task services unimplemented; check the version before relying on newer services, and treat error $82 as "not available".
  • Portability. Use interfaces, bring your own base page, and confine any unavoidable ROM dependency to one labelled place with a version check.
